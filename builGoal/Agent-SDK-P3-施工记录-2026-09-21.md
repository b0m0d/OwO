## 2. 剩余 P3（未完成，按指南条目）

P3 的核心是"唯一 ToolHostService + 收据（receipt）+ change set 驱动的 revert"，
属跨 `owo-agent-policy`/`tool-safety`/`executor`/`core::tools`/server API/桌面 UI 的

1. 建 `ToolHostService` 唯一入口；执行入口强制 capability + receipt sink；
2. 写路径：snapshot → write → diff → receipt；revert 消费 receipt/change set；
3. 审批四动作与 Grant 持久化/撤销在 CLI 与桌面同时接通；
4. 大结果 CAS（preview/ref）；
5. MCP 工具并入同一 effect/policy/capability 流程；
6. 编译负例/契约测试证明"绕过 Policy/Receipt"不可行。

## 5. 2026-09-22 增量安全修复：Session revert 冲突保护

- `SnapshotEntry` 增加向后兼容的 `expected_after_sha256`；`write_file` 仅在成功写入后更新该哈希。对同一文件的后续 Agent 写入先比对当前文件与 Agent 最近一次成功写入哈希；外部编辑或删除时拒绝覆盖，旧快照无写后哈希时仅当文件仍等于原始快照才允许写入。首次读取仅将 `NotFound` 当作新文件，其他读取错误 fail closed。
- `Session::revert` 先预检全部快照文件：当前内容必须仍是 Agent 写入版本，或已等于原始内容；
  发现用户/外部修改时整批拒绝、不先恢复其他文件，并保留快照。旧快照没有写后哈希且文件内容已变化时拒绝覆盖（fail closed）。
- 服务端将冲突返回为 `storage/revert_conflict/not_retryable` HTTP 409，列出冲突相对路径；
  增加真实路由契约测试，并重新生成 `clients/ts/openapi.json`。
- 验证：`owo-agent-core` 全包测试 **183 passed / 1 ignored**（含全部集成目标与 3 个 compile-fail doctest）；服务端 `route_contract_tests` **30/30**；
  `cargo clippy -p owo-agent-server --test route_contract_tests --locked -j 2 -- -D warnings`、
  `cargo fmt --all -- --check`、`git diff --check` 均通过。构建与缓存位于 T 盘 `agent-sdk/target`。

边界：这是对旧 Session 快照回滚的冲突防护，不等于 receipt/change set 驱动的撤销事务；
多文件预检通过后若实际恢复遭遇 I/O 错误，仍可能部分落盘。唯一 ToolHostService、
capability + receipt sink、完整原子撤销与真实 CLI/Desktop 黄金路径仍未完成。

## 8. 2026-09-22 ToolHost capability/receipt 门面增量

本轮把普通 Agent loop 的实际执行路径收口到 core 内部的 `ToolHostService`：

- Agent 创建唯一受信门面，共享现有注册表；串行和只读并发两条执行路径都不再直接
  `ToolRegistry::get().run()`。
- 审批完成后由门面签发带参数 SHA-256 摘要的 `ToolCapability`；未批准调用不能签发，
  未注册工具也不能签发。
- 门面执行完成后，无论工具成功还是失败，都向 `ToolReceiptSink` 写入结构化
  `tool_receipt`，收据只保留工具名、会话、批准状态、成功状态、参数/结果摘要和耗时，
  不把原始参数或结果直接写入收据。原有 `tool_call` 审计仍保留，兼容既有观测与测试。
- 新增 core 单元契约 `tool_host_requires_approval_and_emits_receipt`，覆盖拒绝签发、真实
  执行和 receipt 字段；串行/并发 Agent loop 既有路径继续回归。

验证证据：core 单元 **185 passed / 1 ignored**，`loop_tests` **20/20**，服务端
`route_contract_tests` **32/32**，core/server 定向 Clippy `-D warnings` 均通过，
`cargo fmt --all` 通过；全部构建仍使用 T 盘 target、ORT
解析和 `Invoke-CiCargo` 的 `-j 2 / --test-threads 2` 资源门。

边界：这是普通 Agent 执行入口的第一段统一门面和收据落点，尚不是最终 P3 完成。仍需
把 capability 的签发与 Policy 判定做成不可绕过的类型边界，接入普通写操作的
snapshot → write → diff → receipt/change set 原子流程，并完成真实 CLI/Desktop 的
审批 → diff → revert 黄金路径与绕过负例契约测试。

## 9. 2026-09-22 capability 时效与 nonce 增量

在不改变现有 Agent 调用面和旧审计兼容性的前提下，补上 capability 的最小生命周期约束：

- `ToolHostService::issue` 为每次已批准调用生成 60 秒有效期和 UUID nonce；capability 被
  按值消费，不能由调用方复制出第二次执行入口。
- `ToolHostService::execute` 在查找/运行工具前校验有效期，过期调用返回稳定的
  `approval expired` 错误，不触发工具副作用；成功、失败和过期路径都写 `tool_receipt`。
- receipt/audit 增加 `expires_at_unix` 与 `nonce`，仍只记录参数/结果摘要，不落原始参数和结果。
- 扩展 `tool_host_requires_approval_and_emits_receipt`，覆盖 nonce/expiry 生成、真实执行、
  过期拒绝和收据生命周期字段。

验证：`cargo fmt --all -- --check` exit 0；`owo-agent-core --lib` **185 passed / 1 ignored**；
core 定向 Clippy `-D warnings` exit 0。使用 T 盘 target、ORT 统一解析、`Invoke-CiCargo`
资源门（定向 `-j 2 / --test-threads 2`）。

边界：这只是 capability 生命周期的增量，不等于完整字段绑定。当前仍需继续补齐 tool/version、
workspace/session/turn、effect/scope 的结构化上下文，Policy → capability 的类型不可绕过、
普通写入的 diff/change-set receipt 原子链、MCP 同源执行以及 CLI/Desktop 真机黄金路径。

## 10. 2026-09-22 capability 结构化上下文与失配拒绝

本轮继续补齐 capability 的上下文绑定，避免仅凭工具名、参数和一个批准布尔值重放执行：

- `ToolCapabilityContext` 绑定 workspace、session_id、turn_id 和 scope；Agent 每个回合生成
  独立 turn ID，串行与只读并发工具都从同一上下文签发 capability。
- `ToolHostService::issue` 不再接受裸 `approved: bool`；执行侧先由
  `PermissionRequest + Decision::Allow` 构造 `ToolApprovalGrant`，凭证绑定工具名、参数
  摘要和 request ID，工具名或参数不一致时拒绝签发。
- capability 增加 tool_version、workspace、session_id、turn_id、effect、scope；
  `tool_version` 是工具名、输入 schema、effect 元数据的 SHA-256 指纹，scope 只以摘要写入
  receipt，避免把原始路径/参数扩散到审计记录。
- `ToolReceipt`/`tool_receipt` 审计补充 tool_version、turn_id、effect、scope 摘要；执行前
  拒绝 session、workspace、工具版本失配，继续保留过期拒绝和一次性按值消费语义。
- `tool_host_requires_approval_and_emits_receipt` 新增跨 session 与陈旧 tool_version 的拒绝
  契约，证明失配不会进入工具副作用路径；原有批准拒绝、正常执行、过期拒绝仍保留。

验证：`owo-agent-core --lib` **185 passed / 1 ignored**；新增失配契约包含在该轮测试中；
core `clippy --lib -- -D warnings` exit 0；服务端 `route_contract_tests` **32/32**；
`cargo fmt --all` exit 0。命令均先解析 ORT，再经 `Invoke-CiCargo` 资源门运行，构建产物和
缓存位于 T 盘。

边界：Policy → capability 的类型边界已在 core Agent loop 收紧，但当前仍是 core 内部受信门面，
外部客户端尚不能独立取得这类凭证。普通文件写入尚未统一为 snapshot → write → diff →
receipt / ChangeSet 原子链，MCP、CLI、Desktop 的真实同源黄金路径与 UI/文件/命令三类收据

## 11. 2026-09-22 普通文件写入的执行回执与定向撤销

本轮把普通 `write_file` 经 `ToolHostService` 执行后的文件变化接入可持久化的
`ExecutionReceipt`，但没有把它与 WorkSwarm ChangeSet 混称：

- `Session` 增加执行回执集合；每张回执记录 receipt ID、工具、turn ID、变更文件、写入前后
  SHA-256、diff SHA-256、创建时间和状态。内部恢复所需的 canonical snapshot key 仅用于
  Session/SQLite 持久化，服务端响应不暴露该字段。
- `ToolHostService` 在写工具成功返回后，根据该次写入对应的快照计算变化；无实际变化不生成
  回执。模型/客户端结果和 `ToolReceipt` 审计同时带回 `execution_receipt_id`、变更文件和
  diff 摘要，便于后续 UI 展示和审计关联。
- SQLite schema 升至 v4，新增 `execution_receipts_json`，旧数据库通过迁移自动补列；读取、
  保存、fork 和旧会话兼容路径均已覆盖测试。
- `/session/{id}/revert` 接受可选 `{"receipt_id":"..."}`。指定回执时只回滚该次执行；
  回滚前先对整张回执做当前哈希预检，发现用户编辑即返回既有
  `storage/revert_conflict/not_retryable` 409 且不覆盖文件；通过预检后恢复原内容或删除
  Agent 新建文件，并将回执标记为 `reverted`。OpenAPI 已补充请求体说明。
- 服务端黄金路径现在真实取得持久化 receipt ID，再通过 HTTP `/revert` 指定该 ID 验证：
  用户后改内容时冲突保护成立，恢复 Agent 版本后定向撤销成功。

当前验证：`owo-agent-core --lib` **187 passed / 1 ignored**；core `clippy --lib --locked
-- -D warnings` exit 0；服务端 `route_contract_tests` **32/32**；`cargo fmt --all` exit 0。
所有命令均先解析 ORT，再经 `Invoke-CiCargo` 资源门执行，构建与缓存继续位于 T 盘。

边界：这一步完成的是普通文件写入的 core receipt 与 HTTP 定向撤销基础链，尚不能宣称 P3
完成。UI/文件/命令三类收据全覆盖、MCP 同源执行、CAS 大结果与 change-set 统一语义、真实

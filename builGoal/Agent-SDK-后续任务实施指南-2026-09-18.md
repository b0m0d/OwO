> 文档性质：后续开发的唯一施工入口，不是历史汇报，也不是功能宣传稿。  
> 基线日期：2026-09-18  
> 源码基线：`cec606583d1280af4f6e3ddf506dce84ee5b10be`，叠加当前尚未提交的 R3 工作区改动。  
> 开发范围：仅 `agent-sdk/`。根目录 OwO C++ 输入法工程继续冻结。

## 1. 这份文档解决什么问题

此前重构长期卡住，不是因为某一个错误特别难修，而是因为产品代码、测试脚本、构建链和验收口径同时变化：修复一个现象后，下一次真机运行又暴露另一层问题；部分脚本只检查“文件存在”或“进程启动”，从而把不可用界面判成通过；大批改动长期留在工作区，也使回归来源难以定位。

本指南把后续工作改成以下闭环：

1. 先冻结当前正常冷启动链路，不再继续扩大 R3 功能范围。
2. 先修验收工具的假通过，再执行故障矩阵。
3. 每个故障场景单独完成、单独留证，再运行整套矩阵。
4. R3 分层提交并恢复干净工作区后，才能进入 UI、性能、拆分和发布阶段。
5. 每个任务都必须写明修改文件、行为契约、测试入口和退出条件。
6. “测试通过”不等于“用户可用”；桌面功能必须同时经过代码、接口、壳层和可见界面四层验证。

旧的《Agent-SDK-全项目问题审计与技术重构方案-2026-09-05.md》保留为问题来源和历史记录。本文件负责回答“下一步具体做什么、先后顺序是什么、怎样才算真正完成”。

## 3. 进度卡住的根因与治理办法

### 3.1 产品与验收脚本同时改，失败归因不清

当前 R3 同时修改了服务端认证、事件流、请求台账、Tauri sidecar、前端连接恢复、构建脚本和验收脚本。某个场景失败时，无法快速判断是产品行为错误，还是脚本误判。

治理办法：

- 立即冻结已经通过的正常冷启动产品路径。
- R3 下一批首先只修改验收公共模块和故障矩阵脚本。
- 如果故障矩阵证明确有产品缺陷，再为该场景建立独立修复任务。
- 一个提交不得同时包含“修改场景预期”和“修改产品以满足该预期”，除非提交说明给出旧行为、目标行为和独立复现证据。

### 3.2 验收指标只检查存在性，导致假通过

截图存在不代表截图有效；窗口句柄存在不代表窗口可见；进程存在不代表核心可服务；页面没有统一错误卡也不代表业务输入框可用。

治理办法：所有桌面验收至少同时检查：

- 进程：PID 存活且身份属于本轮启动；
- 服务：`/health`、构建身份、实例身份正确；
- 壳层：窗口句柄重新获取、可见、尺寸达到最低值；
- 页面：通过 CDP 检查可操作 DOM，而不是只看截图；
- 图像：截图尺寸、文件大小、非黑像素比例和内容区域均合格；
- 清理：结束后无孤儿 core、无被改名的真实二进制、无污染用户数据目录。

### 3.3 故障场景的产品契约没有先冻结

“provider 未配置”到底应当算后台连接失败，还是核心正常启动后的配置引导；“core 挂死”是 10 秒内展示提示，还是 45 秒后确认超时，当前脚本没有统一答案。

治理办法：先冻结第 6.2 节的故障契约表，再写断言。断言不能反过来定义产品行为。

### 3.4 大批改动长期不提交，修复无法回滚

R3 工作区同时覆盖服务端、壳、前端、客户端快照和脚本。一旦后续故障修复引入回归，很难定位具体改动。

治理办法：R3 必须按第 6.5 节拆为四个逻辑提交。每个提交独立通过相应测试，最终再跑全量门禁。

### 3.5 旧文档仍把历史绿灯当当前结论

旧报告的绿灯只对当时的代码和当时的检查项有效。新增真机证据已经证明“截图文件存在”不足以作为视觉通过条件。

治理办法：以后每个阶段只有一个当前执行记录；旧记录不删除，但顶部标记“已被哪份证据更新”。状态表必须写证据路径和生成时间。

## 4. 后续开发的强制工作方式

### 4.1 四层验收模型

每项功能按以下层级逐级验收：

| 层级 | 验证内容 | 允许结论 |
|---|---|---|
| L1 静态 | 编译、格式、lint、类型、契约快照 | 代码结构可构建 |
| L2 模块 | 单元测试、组件测试、错误分支 | 模块行为符合局部契约 |
| L3 集成 | 真实服务、HTTP、事件流、sidecar | 组件之间可协作 |
| L4 产品 | 真实桌面窗口、真实交互、截图、用户路径 | 功能对用户可用 |

只有 L4 通过的桌面功能才允许写“完成”。仅 L1/L2 通过必须写“代码完成，尚未真机验收”。

### 4.2 任务切片规则

每个任务卡只允许一个主要目的，并包含：

1. 用户可观察的问题；
2. 明确的行为契约；
3. 允许修改的文件；
4. 禁止顺带修改的范围；
5. 最小自动化测试；
6. 真机验收步骤；
7. 证据目录；
8. 回滚方式；
9. 完成条件。

发现旁支问题时先登记，不得在当前任务中无边界扩张。

### 4.3 构建和安全规则

- 任何手写 Cargo 命令前必须执行 `scripts/resolve-ort.ps1` 的 `Resolve-OwoOrtEnv -Quiet`，禁止复制另一套 ORT 探测逻辑。
- 模型密钥只从环境变量读取，日志、报告、截图和命令输出不得回显密钥。
- 修改服务端路由必须同步 `tests/route_contract_tests.rs`、OpenAPI 快照和 TypeScript schema。
- 默认权限继续 deny；审批与执行必须分离。
- 不修改根目录 OwO C++ 输入法项目。
- 不用真实用户数据目录做桌面验收；每次运行使用独立数据根。
- 不通过改名、删除真实构建产物来模拟故障。

### 4.4 提交规则

- 一个提交只解决一个可描述问题。
- 提交前记录实际执行的测试，不写“理论上通过”。
- 代码提交与纯文档状态回写分开。
- 不把 `docs/qa/evidence/` 中无关历史证据一起加入功能提交。
- 提交后工作区必须能解释所有剩余改动；R3 结束时目标是干净工作区。

## 6. R3：真机桌面验收收口

### 6.1 R3-A1：修复窗口与截图假通过

目标：截图必须能证明窗口确实恢复，不能再把 158×26 的黑线判为通过。

主要文件：

- `scripts/desktop-acceptance-common.ps1`
- `scripts/verify-desktop-cold-boot.ps1`
- `scripts/verify-desktop-failure-matrix.ps1`

具体修改：

1. 将窗口句柄视为短期对象。隐藏、显示、core 重启、WebView 重载后都重新按进程和窗口标题获取 HWND，不复用旧句柄。
2. 新增统一的窗口断言，例如 `Assert-OwoDesktopWindow`：
   - HWND 非零；
   - `IsWindow` 为真；
   - `IsWindowVisible` 为真；
   - `GetWindowRect` 成功；
   - 宽度至少 800、高度至少 520；
   - 窗口不处于最小化状态。
3. 新增统一的截图断言，例如 `Assert-OwoScreenshot`：
   - 文件存在且可以被 `System.Drawing.Image` 解码；
   - 图片宽高与目标窗口尺寸相符；
   - 文件大于合理下限，例如 8 KiB；
   - 对缩略采样像素计算非黑、非透明比例，不能是纯黑、纯透明或单色窄条；
   - 保存实际宽高、字节数和采样比例到报告，而不是只写布尔值。
4. 恢复显示后先等待壳返回 `visible=true`，再重新取 HWND，再等待窗口尺寸稳定，最后截图。
5. 图像只证明“窗口有内容”；最终可用性仍由 CDP DOM 检查承担。恢复后必须再次找到任务输入框，并验证其可聚焦或可输入。

最小测试：

- 人工构造 158×26 黑图，截图断言必须失败。
- 使用真实 900×600 页面截图，断言必须通过。
- 传入已失效 HWND，窗口断言必须重新发现窗口或明确失败，不能静默沿用。

完成条件：重新运行正常冷启动后，报告包含三档截图和恢复截图的真实尺寸、字节数、像素检查；恢复截图不小于 800×520；CDP 确认输入框可操作。

### 6.2 R3-A2：冻结故障场景契约

先把预期写成数据表，再执行脚本。建议将表保存在故障矩阵脚本中的只读场景定义，并在执行记录中复制一份。

| 场景 | 核心是否应启动 | UI 终态 | 必须提供的动作 | 最终错误码/状态 |
|---|---|---|---|---|
| sidecar 缺失 | 否 | 后台组件缺失页 | 重新检查、打开诊断位置 | `core/binary_missing` |
| sidecar 挂死 | 否 | 启动超时页 | 终止并重试 | `core/handshake_timeout` |
| sidecar 早退 | 否 | 后台意外退出页 | 重启后台、查看诊断 | `core/exited` |
| 伪造 ready/身份不匹配 | 否 | 组件身份不一致页 | 重新安装或重新构建 | `core/identity_mismatch` |
| 未选择工作区 | 是 | 工作区引导页 | 选择文件夹 | `workspace/required` |
| provider 未配置 | 是 | 模型配置引导页 | 打开模型设置 | `provider/not_configured` |
| 数据目录不可写 | 否或只读降级 | 存储错误页 | 更换数据目录、重试 | `storage/not_writable` |
| 示例 MCP 关闭 | 是 | 正常主界面 | 可进入工具管理查看禁用原因 | 健康状态，工具标记 disabled |

重要决策：`provider 未配置` 不是 core 连接失败。core 应继续提供本地 API，UI 显示配置引导。脚本不得接受“握手超时”作为该场景通过。

### 6.3 R3-A3：消除故障脚本的结构性风险

主要文件：`scripts/verify-desktop-failure-matrix.ps1`。

具体修改：

1. 将每个场景包装为统一的 `Invoke-OwoFailureScenario`：初始化、启动、采集、断言、清理、写报告六个阶段。
2. 最外层必须有 `try/finally`。任何初始化、复制、编译、启动或断言异常都必须进入清理逻辑。
3. 未处理异常必须落为失败检查：
   - `executed=false`；
   - `passed=false`；
   - 记录异常类型、阶段和脱敏消息；
   - 进程退出码非零。
4. 不再临时改名 `target/debug/owo-agent.exe`。改用每个场景独立的临时运行布局：
   - 从已知构建产物复制 desktop shell 和 sidecar 到场景目录；
   - 缺失场景只删除场景目录中的副本；
   - 壳只在显式验收模式下从该目录发现 sidecar；
   - 验收模式必须由 debug 构建和 `OWO_DESKTOP_ACCEPTANCE=1` 双重约束，release 构建忽略测试覆盖变量；
   - 验收模式禁止回退到仓库或 PATH 中的其他 sidecar，避免历史残留劫持结果。
5. 清理阶段必须验证：壳进程退出、core 进程退出、fault stub 退出、临时目录可删除、真实构建产物哈希未变化。
6. “10 秒内可操作”与“最终故障判定”分开：
   - 10 秒门只要求壳展示加载状态、取消或诊断入口；
   - 最终判定按场景预算执行，例如缺失 15 秒、早退 15 秒、挂死 45 秒；
   - 不允许一边配置 25 秒握手超时，一边要求 10 秒内出现最终超时错误。
7. 错误页动作断言改为按场景定义检查动作 ID，不再只匹配“重新连接”或“打开模型设置”两个中文文案。

完成条件：任意阶段故意抛异常时，报告至少出现 1 个失败项并可靠清理；真实 debug core 不被改名、删除或覆盖。

### 6.4 R3-B：故障矩阵按由快到慢逐项执行

执行顺序：

1. sidecar 缺失；
2. 身份不匹配；
3. 未选择工作区；
4. provider 未配置；
5. 数据目录不可写；
6. 示例 MCP 关闭；
7. sidecar 早退；
8. sidecar 挂死。

每个场景必须独立输出：

- 场景配置快照；
- 壳/core/fault stub 的 PID 与退出状态；
- 脱敏日志；
- CDP DOM 状态；
- 有效截图；
- 断言清单；
- 清理结果；
- 场景级 JSON 报告。

只有单场景通过后才能继续下一个。全部单场景通过后，再运行一次完整矩阵，生成总 `failure-matrix-report.json`。不允许直接反复跑完整矩阵碰运气。

如果某场景失败，按以下顺序归因：

1. 检查场景是否真正注入；
2. 检查壳是否误发现其他 sidecar；
3. 检查服务端事实与 UI 映射是否一致；
4. 检查等待预算和断言是否与冻结契约一致；
5. 最后才修改产品代码。

### 6.5 R3-C：提交拆分

建议拆成以下四个提交，实际文件可按依赖微调，但不得重新合成一个大提交：

1. `feat(server): add bounded request ledger and protected diagnostics`
   - 请求台账、日志去原始 path、OpenAPI/TS/路由契约。
2. `fix(desktop): make auth generation and reconnect lifecycle deterministic`
   - token 每次启动换发、事件流、401/网络恢复、壳重启和订阅重建。
3. `fix(build): stage and verify the exact desktop sidecar`

## 7. R4：UI 信息架构、配置表单和权限中心

### 7.1 目标

用户第一次打开应用时，应能回答四个问题：

1. 我现在可以做什么？
2. 当前后台和模型是否可用？
3. 哪些操作需要审批，为什么？
4. 出错后下一步点哪里？

当前 UI 的根本问题不是颜色或间距，而是功能入口按内部模块命名、状态含义不透明、枚举和路径用自由文本输入、错误提示没有稳定动作。

### 7.2 信息架构

顶层导航控制在五类以内：

| 用户入口 | 包含内容 | 不应直接暴露的内部概念 |
|---|---|---|
| 对话与任务 | 单 Agent 对话、执行进度、结果和中断 | run id、内部调度状态码 |
| 工作区 | 当前目录、变更、diff、恢复 | 原始路径枚举和内部 CAS 结构 |
| 工具与权限 | 工具列表、权限范围、待审批、历史记录 | 策略 JSON 自由文本 |
| 自动化与团队 | 工作流、WorkSwarm、多 Agent 状态 | 未解释的策略缩写 |
| 设置与诊断 | provider、模型、后台状态、日志导出 | 裸环境变量名作为唯一说明 |

导航按钮必须使用“动词/任务 + 一行说明”，不能只显示内部名词或图标。

### 7.3 配置控件替换规则

逐项扫描 `desktop/web/` 中所有 `<input>`、动态表单和 prompt，按下表替换：

| 数据类型 | UI 控件 | 校验 |
|---|---|---|
| 固定枚举 | 单选、下拉或分段按钮 | 只能提交 schema 允许值 |
| 布尔开关 | switch/checkbox | 显示开启后的影响 |
| 文件夹 | 原生目录选择器 | 展示规范化路径和可写状态 |
| 文件 | 原生文件选择器 | 限制扩展名和大小 |
| 权限范围 | 可读树形选择 + 推荐预设 | 显示读/写/执行差异 |
| 模型/provider | 已发现选项 + 自定义高级项 | 连接测试通过后保存 |
| 超时/并发 | 数字控件 + 合理范围 | 禁止任意字符串 |
| 高级 JSON | 折叠的专家模式 | schema 校验并给字段级错误 |

禁止为了省开发时间把枚举、路径、权限和布尔值继续做成纯文本框。

### 7.4 权限中心

新增统一权限中心，至少展示：

- 当前权限配置：只读、工作区写入、命令执行、网络访问；
- 每种权限的影响范围和默认值；
- 待审批请求：工具、参数摘要、目标路径/域名、风险原因；
- “仅本次允许”“本任务允许”“拒绝”三个明确动作；
- 已授权范围和撤销入口；
- 最近审批历史与对应审计记录。

“完全访问”不得是没有解释的一键开关。它必须列出将开放的文件系统、命令和网络范围，并要求用户明确确认。默认仍为 deny。

建议后端契约使用结构化 scope，而不是 UI 拼接字符串：

```text
permission_profile
  filesystem: none | workspace_read | workspace_write | custom
  command: deny | allowlisted | unrestricted
  network: deny | allowlisted | unrestricted
  persistence: once | task | workspace
```

前端提交 profile，服务端展开为现有策略规则；审计记录保存 profile、最终规则和用户决定。

### 7.5 前端拆分

优先拆责任，不做一次性框架迁移：

- `app.js` 只保留启动、路由和全局生命周期；
- `app-domain.js` 拆成 workspace、provider、permission、task 四个域模块；
- 每个 panel 使用 `domain.js`、`render.js`、`controller.js` 三层；
- 网络调用统一经过 `core/api-client.js`；
- SSE 状态统一经过 `core/events.js`；
- 错误展示统一使用 `views/service-error.view.js` 和稳定 action ID；
- 引导页统一使用 `views/setup-guide.view.js`，由原因码选择具体内容。

先选择“权限中心”和“设置与诊断”作为样板，形成模块模板后再迁移其他 panel。

### 7.6 R4 测试与退出条件

- 单元测试覆盖枚举、路径、权限 scope 映射和错误动作。
- 浏览器测试覆盖首次启动、未选工作区、未配置 provider、权限申请、拒绝、单次允许和撤销。
- Tauri 真机测试覆盖原生目录选择、后台断开和重连。
- 900×600、1280×720、1707×1067 三档布局没有被遮挡的主要按钮。
- 用户无需阅读源码即可从 UI 查看功能清单、后台状态和权限状态。
- 不再存在让普通用户直接输入内部枚举值的主流程表单。

## 8. R5：对话和工具调用性能

### 8.1 先测量，不先猜原因

为一次对话建立统一 trace，至少记录：

- 用户提交到服务端接收；
- 排队等待；
- 上下文组装；
- 首个模型请求发出；
- 首 token 返回；
- 工具审批等待；
- 工具进程创建；
- 工具首输出与结束；
- 模型续写；
- UI 首次可见更新与最终完成。

所有时间使用同一 request/run/turn/trace ID 关联。UI 只展示脱敏摘要，详细瀑布放入诊断页。

### 8.2 重点检查项

1. 首屏和对话是否存在重复 HTTP 请求或重复 SSE 订阅。
2. 模型调用前是否串行执行了本可并行的上下文读取。
3. 工具 schema 是否过大、每轮是否重复发送不相关工具。
4. 工具审批后是否重新构建整轮上下文。
5. 命令输出是否必须等进程结束才推送，而不是流式返回。
6. 取消是否在 1 秒内传播到模型请求、工具子进程和 Worker。
7. 慢 MCP 是否阻塞所有工具发现或主对话。
8. WebView 是否因全量 DOM 重绘导致“后台已返回但界面仍慢”。

### 8.3 优化顺序

1. 去重复请求和重复订阅；
2. 工具输出流式化；
3. 上下文读取并行化并设置 deadline；
4. 工具 schema 按任务裁剪和缓存；
5. MCP 单服务隔离、超时和熔断；
6. 前端增量渲染；
7. 最后才考虑更激进的缓存或调度算法。

### 8.4 性能退出条件

在固定机器、固定模型、固定 10 个任务上至少报告 P50/P95：

- 提交到 UI 出现运行状态；
- 提交到模型首 token；
- 工具批准到首输出；
- 取消到模型/子进程停止；
- core 重启到 UI 恢复。

必须同时保存失败率、重复请求数、孤儿进程数和 token 量。没有基线对照的数据不得写“性能显著提升”。

## 9. R6：大文件拆分与死代码清理

### 9.1 拆分原则

- 先锁定行为测试，再做机械移动，最后做逻辑优化。
- 每次只拆一个聚合文件。
- 第一笔只移动代码、修复可见性和 import，不改变接口。
- 第二笔再消除重复、收紧类型和修改内部接口。
- 每次拆分后比较路由快照、公开 API 和关键测试数量。

### 9.2 建议拆分顺序

#### A. `owo-agent-server/src/lib.rs`

目标结构：

```text
server/
  bootstrap.rs
  app_state.rs
  router.rs
  middleware.rs
  shutdown.rs
```

`lib.rs` 只导出公共类型和启动入口。路由注册集中在 `router.rs`，状态装配放 `app_state.rs`，启动/关闭生命周期放 `bootstrap.rs` 和 `shutdown.rs`。

#### B. `owo-agent-core/src/workswarm.rs`

目标结构：

```text
workswarm/
  mod.rs
  domain.rs
  planner.rs
  scheduler.rs
  executor.rs
  recovery.rs
  policy.rs
  events.rs
```

先按现有类型和函数依赖移动，不重写算法。`mod.rs` 只保留稳定 facade。

#### C. `desktop/web/panels/workswarm.panel.js`

目标结构：

```text
panels/workswarm/
  domain.js
  api.js
  controller.js
  render.js
  actions.js
  selectors.js
  format.js
```

禁止 render 函数直接发请求；禁止 API 模块直接操作 DOM；controller 负责把事件映射为状态变化。

#### D. `product_eval.rs`

拆为 suite、runner、metrics、report、pricing、artifact。报告生成不得参与任务执行状态机。

### 9.3 死代码处理流程

死代码分为四类：

1. 编译器不可达或无引用代码；
2. 已无入口但仍能编译的功能；
3. 被新实现替代的历史脚本/页面；
4. 仅测试或迁移兼容需要的保留代码。

每项在 `docs/internal/dead-code-inventory.md` 中记录：符号/文件、引用证据、运行入口、保留原因、删除风险、替代实现和验证方式。

删除前至少完成：

- 全仓引用搜索；
- 路由/命令/动态注册检查；
- 文档和脚本入口检查；
- 对应测试确认；
- 小提交删除；
- 全量门禁。

无法证明无入口的代码标记为“疑似死代码”，不得直接删除。

### 9.4 R6 退出条件

- 上述三个最大聚合文件都有清晰模块边界；
- 公开契约和路由无意外变化；
- 死代码清单中每项都有结论，不再只写文件名；
- 删除项可从 Git 单独恢复；
- 编译、测试、桌面主链和故障矩阵全部通过。

## 11. R8：单 Agent 与 Codex 的差距评测

### 11.1 不再用功能列表主观比较

建立固定 10 个任务，至少覆盖：

- 读取并解释代码；
- 小范围修复；
- 跨文件实现；
- 运行测试并修复失败；
- 工具审批；
- 命令长输出；
- 用户中途取消；
- core 重启恢复；
- 无权限写入；
- 失败后继续任务。

同一任务使用相同仓库快照、模型、提示、权限和时间预算分别运行 OwO 单 Agent 与对照系统。

### 11.2 评测指标

- 任务成功率；
- 首次有效动作时间；
- 总耗时；
- 用户需要干预次数；
- 无效工具调用数；
- 重复读取/重复请求数；
- 审批体验；
- 取消和恢复可靠性；
- diff 正确性；
- token 与估算成本。

最终结论按“已相当、部分具备、明显缺失、尚未验证”四档写，禁止用“接近 Codex”替代数据。

## 12. 文档、证据与状态回写

每个阶段保留三类产物：

1. 执行记录：做了什么、为何这样做、哪些未做；
2. 机器证据：JSON、日志、截图、哈希、测试输出；
3. 状态索引：当前阶段、负责人、提交和证据路径。

状态条目模板：

```text
任务 ID：R3-A1
状态：未开始 / 进行中 / 阻塞 / 已完成
源码基线：<commit>
允许修改：<files>
行为契约：<expected behavior>
自动化验证：<commands and results>
真机验证：<steps and results>
证据目录：<path>
提交：<commit>
剩余风险：<known limitations>
```

回写规则：

- 证据数字改变时，执行记录、协调表和本指南状态必须同步。
- 旧报告保留，但在顶部注明已被新报告取代。
- 截图必须记录尺寸和采集对象；日志必须脱敏。
- 不把“脚本启动成功”写成“场景通过”。

## 15. 最终完成定义

本轮系统性重构只有在以下条件同时成立时才能结束：

1. 桌面端双击启动后后台自动连接，真实窗口可见且可操作；
2. 后台缺失、挂死、早退、身份不匹配、配置缺失和存储失败都有明确可恢复界面；
3. UI 能直接说明功能、状态和下一步操作，主流程不要求输入内部枚举字符串；
4. 权限默认拒绝，但用户可清楚选择单次、任务级和工作区级授权，并可撤销；
5. 对话和工具调用有可观测的分段耗时，并以固定任务数据证明性能改进；
6. 大文件按稳定边界拆分，死代码按证据删除；
7. 所有路由、权限、diff/revert、会话和审计契约保持工作；
8. 新安装包由干净源码构建，壳和 sidecar 身份一致；
9. 正常路径、故障矩阵、安装包和固定任务集都有可追溯证据；
10. 工作区干净，文档状态与源码和证据一致。

在达到这些条件前，后续工作应按本指南的阶段门逐项推进，不再用“继续修一些问题”的方式扩大任务范围。

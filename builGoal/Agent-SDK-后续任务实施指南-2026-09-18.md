## 2. 统一施工规则

### 2.1 四层完成标准

| 层级 | 验证内容 | 允许使用的结论 |
|---|---|---|
| L1 静态 | 编译、格式、clippy、类型、快照 | 代码可以构建 |
| L2 模块 | 单元测试、组件测试、错误分支 | 局部行为符合契约 |
| L3 集成 | HTTP、SSE、真实 core、sidecar、持久化 | 模块可以协作 |
| L4 产品 | 真实桌面窗口、实际点击、截图、恢复和安装包 | 功能对用户可用 |

桌面功能只有 L4 通过才能写“完成”。仅单元测试通过，应写“源码完成，真机待验收”。

### 2.2 任务边界

每个任务必须同时写清：

- 用户可观察的问题；
- 目标行为和错误行为；
- 允许修改的文件；
- 明确禁止顺带修改的文件；
- 自动化测试；
- 真机验收；
- 证据目录；
- 单独提交；
- 回滚方式。

禁止再使用“继续优化”“顺便修复其他问题”这种无法验收的任务描述。

### 2.3 构建、权限和凭据规则

- 任何手写 Cargo 命令前先通过 `scripts/resolve-ort.ps1` 注入 ORT 环境。
- 本机 Rust 编译和测试必须遵守第 2.4 节的资源安全红线，禁止 Cargo 按 32 个逻辑处理器自动展开高并发。
- 模型凭据只能来自环境变量，日志、截图、JSON 和命令输出不得回显秘密。
- 修改服务端路由必须同步 `route_contract_tests.rs`、OpenAPI 和 TypeScript schema。
- 权限默认 deny；审批与主 Agent 执行分离。
- 桌面验收必须使用独立数据根，不能污染真实用户目录。
- 任何故障测试不得删除、覆盖或改名真实构建产物。
- 一个提交只解决一个主要问题；代码提交和纯文档回写分开。

### 2.4 Rust 编译与测试资源安全红线

本机为 32 逻辑处理器、约 32 GB 内存。`owo-agent-core` 含大量单元测试、36 个集成测试文件，并链接 ONNX Runtime、Sherpa ONNX、SQLite 和 Windows 原生依赖。未限制的 Cargo 会同时启动大量 `rustc`、`link.exe` 和测试线程，导致物理内存耗尽、系统分页和整机卡死，影响用户正在进行的其他任务。

以下规则是强制要求，不是性能建议：

1. **普通开发和定向测试：编译并发上限 2，测试线程上限 2。**
2. **完整 workspace、完整 core、release 或原生依赖重建：编译并发固定为 1，测试线程固定为 1。**
3. **禁止依赖 Cargo 默认并发。** 所有手写命令必须显式传入 `-j 1` 或 `-j 2`，同时传入 `--test-threads=1` 或 `--test-threads=2`。
4. **禁止同时运行两组 Cargo。** 开始编译前检查是否已有 `cargo`、`rustc` 或 `link.exe`；存在时等待当前任务结束，不得再启动第二个构建。
5. **禁止使用 `--quiet` 配合 `Select-Object -Last` 隐藏长任务进度。** 长任务必须持续显示阶段、运行时间或日志尾部，让用户可以判断是在运行还是挂起。
6. **15 分钟 timeout 不是资源保护。** 超时只限制持续时间，不限制瞬时内存；不能用较长 timeout 替代并发限制。
7. **内存保护阈值：**可用物理内存低于 6 GB，或系统内存使用率达到 80% 时，不得启动新的 Rust 构建；运行中的构建应停止派生新测试分片，必要时中止并改用 `-j 1`。
8. **不得为了缩短门禁时间提高并发。** 用户正在使用电脑时，工程测试必须让出资源；测试耗时增加可以接受，整机卡顿不可接受。
9. **构建缓存大小不等于可用内存。** `target/` 很大时仍必须限制并发，禁止以“依赖已经缓存”为由恢复默认 32 路构建。
10. **执行结果必须保存真实退出码。** 不能因为中止、OOM 或管道隐藏输出而将测试记为通过。

#### 2.4.1 普通单元测试标准命令

```powershell
cd T:\创新创业\OwO-master\agent-sdk
. .\scripts\resolve-ort.ps1
Resolve-OwoOrtEnv -Quiet | Out-Null
$env:CARGO_BUILD_JOBS = "2"
$env:RUST_TEST_THREADS = "2"
cargo test -p owo-agent-core --lib --locked -j 2 -- --test-threads=2
$code = $LASTEXITCODE
"CORE=$code"
```

#### 2.4.2 单个集成测试标准命令

```powershell
$env:CARGO_BUILD_JOBS = "2"
$env:RUST_TEST_THREADS = "2"
cargo test -p owo-agent-core --test gateway_tests --locked -j 2 -- --test-threads=2
```

必须按集成测试文件逐个运行，不得一次并行启动多个 `cargo test --test ...` 进程。

#### 2.4.3 完整测试和 release 构建标准

```powershell
$env:CARGO_BUILD_JOBS = "1"
$env:RUST_TEST_THREADS = "1"
cargo test -p owo-agent-core --locked -j 1 -- --test-threads=1
```

完整 workspace 测试、Tauri release、安装包和需要重新链接 ONNX/Sherpa 的任务同样使用 `-j 1`。只有纯 JavaScript、文档或不调用 Rust 编译器的任务不受此限制。

#### 2.4.4 脚本必须实施的保护

后续修改 `scripts/ci-shared.ps1`、`scripts/ci-gate.ps1`、开发启动脚本和安装包脚本，统一增加：

- 默认注入 `CARGO_BUILD_JOBS=2`、`RUST_TEST_THREADS=2`；
- 完整测试或 release 模式自动降为 1；
- 检测并拒绝超过 2 的本机并发参数；
- 检测已有 Cargo/Rust/Link 进程，避免重复启动构建；
- 运行前读取可用内存，低于 6 GB 时直接拒绝启动并给出说明；
- 长步骤每 30 秒输出心跳、当前阶段和持续时间；
- 被中止或资源保护触发时写入 `interrupted/resource_limited`，退出码必须非零；
- 将资源限制写入 `summary.json`，便于证明测试是在安全参数下运行。

如果构建已经导致系统卡顿，优先 `Ctrl+C` 停止当前命令；仍有残留时，只终止本轮 Rust 构建进程，不结束用户的其他应用：

```powershell
Get-Process cargo,rustc,link -ErrorAction SilentlyContinue | Stop-Process -Force
```

### 2.5 统一错误模型

后端、壳和 UI 使用同一错误对象，避免各层自由拼文案：

```text
error
  code            稳定错误码，例如 core/binary_missing
  layer           shell | core | provider | workspace | storage | tool
  summary         用户可读的一句话
  detail          脱敏诊断信息
  recoverable     是否可恢复
  actions[]       稳定动作 ID、标题和参数
  trace_id        可关联日志和请求台账
```

UI 根据 `code` 和 `actions[].id` 渲染，不通过匹配中文文案判断错误类型。

#### 3.3.1 窗口身份检查

### 3.4 R3-B：冻结八个故障契约

| 场景 | core 预期 | UI 终态 | 必须提供的动作 | 目标错误码 |
|---|---|---|---|---|
| sidecar 缺失 | 不启动 | 后台组件缺失 | 重新检查、打开诊断位置 | `core/binary_missing` |
| sidecar 挂死 | 启动失败 | 启动超时 | 终止并重试 | `core/handshake_timeout` |
| sidecar 早退 | 启动后退出 | 后台意外退出 | 重启后台、查看诊断 | `core/exited` |
| 身份不匹配 | 拒绝接入 | 组件身份不一致 | 重新安装或重建 | `core/identity_mismatch` |
| 未选工作区 | 正常运行 | 工作区引导 | 选择文件夹 | `workspace/required` |
| provider 未配置 | 正常运行 | 模型配置引导 | 打开模型设置、测试连接 | `provider/not_configured` |
| 数据目录不可写 | 启动失败或只读降级 | 存储错误 | 更换数据目录、重试 | `storage/not_writable` |
| 示例 MCP 关闭 | 正常运行 | 正常主界面 | 可查看禁用原因 | 工具状态 `disabled` |

时限拆成两层：

- 10 秒内：壳必须出现加载状态、取消或诊断入口；
- 最终状态：缺失/早退 15 秒，身份错误 20 秒，挂死 45 秒，业务引导 20 秒。

### 3.5 R3-C：执行顺序

按由快到慢执行，避免每次等待完整矩阵：

1. sidecar 缺失；
2. 身份不匹配；
3. 未选择工作区；
4. provider 未配置；
5. 数据目录不可写；
6. 示例 MCP 关闭；
7. sidecar 早退；
8. sidecar 挂死。

每个场景独立生成：场景配置、进程身份、日志、DOM 事实、截图、断言、清理结果和 JSON 报告。八个场景单独通过后，才运行完整矩阵并生成 `failure-matrix-report.json`。

### 3.6 R3-D：门禁可观察性

为 `ci-gate.ps1` 增加：

- 按第 2.4 节强制限制 Rust 编译和测试并发，普通定向测试最多 2，完整测试固定为 1；
- 运行前检查已有 Cargo 进程和可用内存，禁止重叠构建或在可用内存低于 6 GB 时启动；
- 每个长步骤每 30 秒输出一次已运行时长；
- 每步独立超时和超时错误码；
- 测试输出同时写文件，终端显示最近进度；
- `summary.json` 在每步结束后增量更新，而不是只在整个脚本结束后生成；
- 被用户中止时写 `interrupted=true`，不能留下没有结论的空报告。

这项改动只改善门禁可观察性，不允许通过缩短测试或吞掉失败来“提速”。

## 4. R4：功能使用、UI 与权限系统优化

### 4.1 R4 目标

R4 不只是“调整界面”，而是让用户能够理解和完成核心任务：

- 知道产品有哪些功能；
- 知道后台、工作区和模型是否可用；
- 不需要输入内部枚举、JSON 或完整路径；
- 清楚工具为什么申请权限、会影响什么、如何撤销；
- 出错后有明确动作，而不是只看到连接失败。

### 4.2 功能信息架构

顶层导航控制为五类：

| 导航 | 用户任务 | 主要页面 |
|---|---|---|
| 对话与任务 | 提问、执行、查看进度、取消 | 会话、任务状态、结果 |
| 工作区 | 选择项目、查看变更、diff、撤销 | 项目、ChangeSet、历史 |
| 工具与权限 | 查看工具、审批、授权和撤销 | 工具目录、权限中心、审批历史 |
| 自动化与团队 | 工作流、WorkSwarm、多 Agent | 自动化、团队、人工待办 |
| 设置与诊断 | 模型、后台、日志和性能 | provider、连接、诊断台账、trace |

每个导航按钮采用“中文任务名 + 一行说明”，内部名词如 WorkSwarm、MCP、Trace 放在说明或开发者模式，不作为普通用户唯一标签。

### 4.3 全局状态条

主窗口顶部增加统一状态条，显示：

- 后台：正在启动 / 可用 / 降级 / 失败；
- 工作区：名称、路径摘要、只读/可写；
- 模型：provider、模型、连接状态；
- 权限：当前 profile 和待审批数量；
- 当前任务：运行、等待审批、已取消或已完成。

所有状态点击后进入对应页面，不能只是不可交互的文字灯。

### 4.4 表单控件规范

| 数据 | 控件 | 禁止做法 |
|---|---|---|
| 固定枚举 | 下拉、单选、分段按钮 | 纯文本输入内部值 |
| 布尔值 | 开关，并说明影响 | 输入 `true/false` |
| 文件夹 | Tauri 原生目录选择器 | 要求手输完整路径 |
| 文件 | 原生文件选择器和扩展名限制 | 无限制文本框 |
| provider/模型 | 已发现选项 + 高级自定义 | 只显示环境变量名 |
| 权限范围 | 预设 + 树形范围选择 | 自由填写策略 JSON |
| 并发/超时 | 数字框、范围和单位 | 任意字符串 |
| 标签集合 | chips、多选列表 | CSV 文本 |
| 时间 | date/time/datetime 控件 | 手填 RFC3339 |

高级 JSON 只允许在开发者模式中折叠显示，并必须通过 schema 校验后才能保存。

### 4.5 统一权限中心

新增独立“工具与权限”页面，不再把权限能力散落在审批条、工作流和设置页。

#### 4.5.1 用户看到的内容

- 当前权限预设：只读、工作区编辑、受控执行、自定义；
- 文件系统、命令和网络三个维度的实际范围；
- 待审批请求；
- 已授权范围和有效期；
- 最近审批历史；
- 撤销入口；
- “完全访问”的风险拆解。

#### 4.5.2 审批动作

统一为：

- 拒绝；
- 仅本次允许；
- 本任务允许；
- 工作区长期允许。

“完全访问”不得是一键模糊开关。选择后必须列明：允许访问的目录、命令范围、网络范围、持续时间和不可逆风险，再要求二次确认。

#### 4.5.3 后端结构

前端提交结构化 profile：

```text
filesystem: none | workspace_read | workspace_write | custom
command: deny | allowlisted | unrestricted
network: deny | allowlisted | unrestricted
persistence: once | task | workspace
scopes[]
```

服务端将 profile 展开为策略规则；审计记录保存 profile、最终规则、请求摘要、用户决定和撤销记录。工具参数必须脱敏，文件路径只展示必要范围。

### 4.6 诊断请求台账接入

现有 `GET /diagnostics/requests` 必须接入“设置与诊断”页。

页面至少显示：

- 最近请求数量；
- health、auth、events、business 四类计数；
- 慢请求 Top N；
- 按路由模板聚合的 P50/P95；
- 来源 web/shell；
- 最近一次 core 重启；
- SSE 当前连接数；
- 一键导出脱敏诊断包。

禁止显示原始 URL query、Bearer、配对秘密、用户输入全文或未经处理的本地绝对路径。

### 4.7 错误页与恢复动作

统一使用稳定 action ID：

```text
retry_core
open_provider_settings
choose_workspace
choose_data_directory
open_diagnostics
copy_trace_id
reinstall_component
```

错误页必须回答：发生了什么、是否影响数据、用户现在能做什么、在哪里查看详细诊断。相同错误码在首次启动、运行中断线和恢复失败时使用相同术语。

### 4.8 前端结构调整

在 R4 内只拆与当前功能直接相关的前端边界：

- `app.js`：只保留 boot、路由和全局生命周期；
- `app-domain.js`：拆成 `workspace-domain.js`、`provider-domain.js`、`permission-domain.js`、`task-domain.js`；
- 权限中心使用 `domain.js`、`api.js`、`controller.js`、`render.js`；
- 网络请求只经过 `core/api-client.js`；
- SSE 只经过 `core/events.js`；
- render 函数不得发 HTTP；
- API 模块不得直接操作 DOM。

### 4.9 CLI/TUI 使用优化

桌面端是主入口，但 CLI 必须保留清晰的开发者体验：

- 连接、模型、工作区、权限和任务状态使用同一套中文术语；
- 工具调用显示“等待审批 / 执行中 / 流式输出 / 已取消 / 失败”；
- 错误输出包含稳定错误码和下一步命令；
- 宽字符、窄窗口、长路径和流式输出继续维护快照测试；
- 非交互命令提供稳定 JSON 输出，不混入进度动画。

### 4.10 R4 真机验收

使用浏览器测试验证 DOM 和交互，使用真实 Tauri 验证原生目录选择、窗口尺寸和连接恢复。

必须覆盖：

- 首次启动；
- 未选工作区；
- provider 未配置；
- 后台断开和重连；
- 权限拒绝、单次允许、任务级允许、撤销；
- 900×600、1280×720、1707×1067；
- 键盘导航、焦点可见、缩放 125%/150%；
- 空态、加载态、错误态、数据很多的状态。

### 4.11 R4 退出条件

- [ ] 普通用户能从 UI 直接查看功能地图和系统状态。
- [ ] 主流程不再要求输入内部枚举、CSV、JSON 或完整文件夹路径。
- [ ] 权限中心可查看、授权、拒绝和撤销。
- [ ] “完全访问”具有范围、持续时间和风险说明。
- [ ] 请求台账、SSE、慢请求和 core 重启可在诊断页查看。
- [ ] 八类 R3 错误都能从 UI 执行对应恢复动作。
- [ ] 三档窗口和高 DPI 真机视觉验收通过。

## 5. R5：对话与工具调用性能闭环

### 5.1 R5 原则

先建立基线，再优化；必须区分模型网络耗时、Agent 自身开销、审批等待、工具执行和 UI 渲染。不能把 provider 慢全部归因于本地程序，也不能用主观体感代替数据。

### 5.2 统一 trace 时间线

每轮对话记录：

```text
ui_submit_at
server_received_at
queue_entered_at / queue_left_at
context_started_at / context_finished_at
model_request_at / first_token_at / model_finished_at
approval_requested_at / approval_decided_at
tool_spawn_at / tool_first_output_at / tool_finished_at
persistence_started_at / persistence_finished_at
ui_first_update_at / ui_final_at
cancel_requested_at / cancel_completed_at
```

所有事件使用同一 `trace_id`、`turn_id`、`run_id`。时间采用单调时钟计算耗时，UTC 时间只用于跨进程关联。

### 5.3 固定性能任务集

至少建立十个任务：

1. 纯文本短问答；
2. 读取单文件；
3. 搜索多个文件；
4. 修改单文件并生成 diff；
5. 运行短命令；
6. 运行持续输出命令；
7. 需要一次审批的工具；
8. 用户取消；
9. MCP 慢响应/超时；
10. core 重启后恢复对话。

固定机器、模型、上下文、权限 profile 和仓库快照。每个任务至少重复 20 次，输出 P50、P95、失败率和异常值。

### 5.4 性能指标与目标

| 指标 | 建议目标 | 说明 |
|---|---:|---|
| 提交到 UI 显示“运行中” | P95 ≤150 ms | 本地 UI 响应 |
| 本地非模型 API | P95 ≤200 ms | 不含长任务 |
| SSE 到 UI 可见更新 | P95 ≤200 ms | 服务端发布到渲染 |
| Agent 模型前置开销 | P95 ≤500 ms | 不含 provider 网络 |
| 审批决定到工具派发 | P95 ≤300 ms | 不含工具自身启动 |
| 工具启动到首输出 | 分工具报告 | shell、MCP、文件工具分别统计 |
| 取消到模型请求停止 | P95 ≤1 s | 支持取消的 provider |
| 取消到子进程结束 | P95 ≤1 s | 孤儿进程为 0 |
| core 重启到 UI 恢复 | P95 ≤10 s | bearer 换代和 SSE 重建 |
| 隐藏窗口请求增量 | 0 | 五分钟观察窗口 |

首 token 绝对耗时受远程模型影响，报告必须拆成“本地前置开销”和“provider 等待”。

### 5.5 优化顺序

#### A. 网络和刷新

- 保持单一 SSE 连接；
- 相同路由请求在飞行期间合并；
- 失效事件按域去重，使用短时间批处理；
- 页面隐藏时停止非必要请求，恢复后只补刷失效域；
- 401 或 core 代际变化只触发一次重握手；
- 请求设置 deadline，超时后取消底层工作。

#### B. 上下文和模型调用

- 独立上下文源并行读取；
- 缓存稳定的 AGENTS/技能索引，按文件变更失效；
- 工具 schema 按任务裁剪，不每轮发送全部 MCP schema；
- compaction 使用 Fast 档，但必须保留源引用；
- 模型流式 token 到达后立即推送，不等待持久化完成。

#### C. 工具调用

- 审批通过后复用已验证参数，不重新构建整轮上下文；
- 命令 stdout/stderr 分块流式发送；
- MCP 服务分别设置连接、首响应和总超时；
- 单个 MCP 故障不能阻塞其他工具；
- 取消先通知，再有界等待，超时后终止进程树；
- 工具结果过大时保存 Artifact，只把摘要和引用送回模型。

#### D. 存储与 UI

- 避免每个 token 同步写数据库；按批次或终态持久化；
- 大列表使用增量渲染或虚拟化；
- markdown 流式更新限制重排频率；
- 避免全页面重新 render；按域更新；
- 慢日志、trace 和审计列表分页加载。

### 5.6 性能诊断页面

诊断页展示最近一次和最近 20 次：

- 总耗时；
- 模型、审批、工具、存储、UI 分段瀑布；
- 首 token；
- 工具首输出；
- 重试、超时和取消；
- 请求数量与重复请求；
- token、上下文大小、schema 大小；
- 当前 P50/P95 与基线差值。

### 5.7 R5 退出条件

- [ ] 十任务基线报告可重复生成。
- [ ] 每个阶段都有可靠时间戳和 trace 关联。
- [ ] 固定任务输出 P50/P95、失败率、请求数和 token。
- [ ] 至少解决三项实测最大的性能瓶颈。
- [ ] 优化前后使用相同任务和配置对照。
- [ ] 取消后孤儿模型请求、命令进程和 Worker 为 0。
- [ ] 性能诊断页可查看并导出脱敏报告。

## 6. R6：结构拆分与死代码治理

### 6.1 R6 原则

- 先冻结测试，再机械移动，最后优化逻辑。
- 第一笔拆分只移动代码和调整可见性，不改变行为。
- 每次只拆一个聚合文件。
- 公开 API、路由、序列化格式和事件名称保持不变。
- 每次拆分形成独立提交，可单独 revert。

### 6.2 服务端 `lib.rs`

目标结构：

```text
owo-agent-server/src/server/
  mod.rs
  bootstrap.rs
  app_state.rs
  router.rs
  middleware.rs
  shutdown.rs
  openapi.rs
```

职责：

- `bootstrap.rs`：配置解析、数据目录、启动顺序；
- `app_state.rs`：共享依赖构造；
- `router.rs`：路由聚合；
- `middleware.rs`：认证、请求台账、日志、CORS；
- `shutdown.rs`：优雅关闭和恢复；
- `openapi.rs`：公开契约生成。

目标：`lib.rs` 控制在 300 行以内，单模块原则上不超过 600 行。

### 6.3 Core `workswarm.rs`

目标结构：

```text
workswarm/
  mod.rs
  domain.rs
  planner.rs
  scheduler.rs
  executor.rs
  policy.rs
  recovery.rs
  persistence.rs
  events.rs
  metrics.rs
```

依赖方向：domain 不依赖执行器；planner 只依赖 domain/policy；executor 不负责持久化格式；recovery 通过 facade 调度，不直接拼内部状态。

目标：`mod.rs` 不超过 400 行，其他模块原则上不超过 900 行。

### 6.4 Core `product_eval.rs`

目标结构：

```text
product_eval/
  mod.rs
  suite.rs
  runner.rs
  executor.rs
  metrics.rs
  report.rs
  pricing.rs
  artifact.rs
```

任务定义、实际执行、指标聚合和报告渲染必须分离。报告代码不得影响任务执行状态机。

### 6.5 Web `workswarm.panel.js`

在已有 `domain.js`、`format.js`、`render.js` 基础上继续拆：

```text
panels/workswarm/
  domain.js
  api.js
  controller.js
  actions.js
  selectors.js
  render.js
  format.js
```

边界：

- `api.js` 只负责请求与响应转换；
- `controller.js` 负责生命周期和状态迁移；
- `actions.js` 负责用户动作；
- `selectors.js` 只派生视图数据；
- `render.js` 为纯函数，不访问网络；
- panel 入口只装配模块。

目标：入口文件低于 500 行，其余模块原则上低于 700 行。

### 6.6 Web `app.js` 与 `app-domain.js`

目标结构：

```text
app/
  bootstrap.js
  routes.js
  lifecycle.js
  global-events.js
domains/
  session.js
  task.js
  workspace.js
  provider.js
  permission.js
  diagnostics.js
```

先迁移 R4 新增的权限和诊断功能作为样板，再迁移旧逻辑。不得在拆分过程中改为新框架或一次性重写全部前端。

### 6.7 死代码分类

| 类型 | 判定方法 | 处理 |
|---|---|---|
| 编译期不可达 | 编译器告警、无引用符号 | 补验证后删除 |
| 无入口功能 | 无路由、命令、动态注册和 UI 入口 | 建立替代关系后删除 |
| 历史重复实现 | 新旧脚本或页面同时存在 | 保留唯一入口，迁移调用后删除旧版 |
| 兼容代码 | 旧数据/旧协议仍可能读取 | 写移除版本和迁移条件 |
| 测试专用 | 仅 fixture、stub、feature gate 使用 | 放入明确测试目录或保留 |

### 6.8 死代码清理流程

每项在 `docs/internal/dead-code-inventory.md` 记录：

- 文件或符号；
- 静态引用结果；
- 路由/CLI/动态注册检查；
- 运行时命中证据；
- 是否有持久化兼容责任；
- 替代实现；
- 删除测试；
- 删除提交。

无法证明无入口的代码只能标记“疑似死代码”，不得直接删除。

### 6.9 重复代码和契约单一来源

重点排查：

- 构建身份和 sidecar 查找规则是否重复；
- 错误码与中文文案是否多处维护；
- 前端路由和 panel 列表是否重复；
- OpenAPI、TS schema 和手写 DTO 是否漂移；
- 权限 effect 是否在工具、UI 和策略层重复推断；
- 性能指标字段是否在 trace、observability 和报告中各自命名。

每类只能保留一个事实源，其他层从事实源生成或映射。

### 6.10 R6 退出条件

- [ ] server `lib.rs`、core `workswarm.rs`、`product_eval.rs` 完成职责拆分。
- [ ] web `workswarm.panel.js`、`app.js`、`app-domain.js` 完成分层。
- [ ] 路由、OpenAPI、事件名和持久化格式无意外变化。
- [ ] 死代码清单每项都有删除、保留或延期理由。
- [ ] 删除代码按小提交组织，能独立恢复。
- [ ] 格式、clippy、全测试、R3 主链和故障矩阵无回归。
- [ ] 文档中的模块结构和真实目录一致。

## 7. 跨主线优化建议

### 7.1 功能使用

- 普通模式只展示完成任务所需功能，高级系统默认折叠到开发者模式。
- 所有空态都提供下一步按钮，不只显示“暂无数据”。
- 每个长任务提供进度、取消和恢复入口。
- 每个功能页提供一句“这个功能解决什么问题”。
- 先完成权限中心和诊断页两个样板，再迁移其他复杂 panel。

### 7.2 性能

- 优先消除重复请求、重复 SSE、串行上下文和全量 DOM 重绘。
- 对远程模型、MCP、命令和本地 API 分别统计，避免平均数掩盖根因。
- 将性能回归纳入固定十任务，不用临时人工体验替代。
- 为 CI 长步骤增加心跳和超时，减少“到底在跑还是卡死”的排查时间。

### 7.3 Bug 治理

- 每次真实验收发现的假绿色都必须补一个负例测试。
- 同类错误统一稳定错误码和 action ID。
- 问题报告必须包含复现条件、预期、实际、trace ID、日志和截图。
- 修复后先跑最小复现，再跑所属模块，最后跑完整门禁。
- 运行时故障不能只靠增加等待时间掩盖。

### 7.4 架构

- 保持 core 不依赖 UI，UI 不推断 core 内部状态。
- 服务端负责领域事实，桌面壳负责生命周期，WebView 负责展示和用户动作。
- PowerShell 脚本只做编排，不复制 Rust 中的业务规则。

## 12. R3–R6 总完成定义

只有以下条件全部成立，才可宣布本计划完成：

1. 桌面端正常启动和八个故障场景都有可信真机证据；
2. 验收脚本能够识别黑图、窄条、失效窗口、场景未执行和清理失败；
3. 用户可以从 UI 理解主要功能、后台状态、模型状态和工作区状态；
4. 主流程不要求输入内部枚举、CSV、原始 JSON 或完整目录路径；
5. 权限中心支持拒绝、单次、任务级、工作区级授权和撤销；
6. 诊断页能查看请求台账、SSE、慢请求、trace 和性能瀑布；
7. 十任务基准给出优化前后 P50/P95、失败率、请求数和 token；
8. 取消后没有孤儿模型请求、工具进程或 Worker；
9. 六个主要聚合文件完成职责拆分，公开契约无漂移；
10. 死代码按引用、入口和运行证据删除，不靠主观判断；
11. 全量门禁、真机主链和故障矩阵均取得明确成功终态；
12. 执行记录、协调表、本计划和机器证据保持一致。

R7 安全发布和 R8 Codex 对标在上述条件完成后启动。当前不得使用旧安装包或历史单元测试替代 R3–R6 的产品验收。

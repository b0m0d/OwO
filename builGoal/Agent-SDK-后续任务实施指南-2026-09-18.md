> 文档性质：当前最高优先级施工方案，替代原 R3–R6 顺序计划。
> 更新日期：2026-09-19。
> 当前分支：`agent-frame`。

## 0. 最高优先级决策

当前工程不再继续以“增加路由、面板和实验功能”为主线。即日起先完成 **A0–A5 架构重构**，目标是把产品收敛为一个真正可用的本地 Agent：

1. 双击桌面端后快速出现可操作界面；
2. 后台只存在一份权威 Agent 运行时；
3. CLI、TUI、桌面共享同一会话、权限、工具和诊断状态；
4. 模型 token 真正实时显示，不再整段缓存后“假流式”回放；
5. 基本文件读取、搜索、写入、命令、审批、diff、撤销形成稳定闭环；
6. 新增普通 Agent 功能时主要修改 Python/TypeScript，不再被 ONNX、Windows 原生库和整个 Rust workspace 拖住；
7. Rust 只保留在确实需要系统安全、原生能力和稳定二进制边界的位置。

### 0.1 路线结论

本项目不采用“每个模块一个微服务”的云原生拆分，也不把十几个 Rust crate 伪装成微服务。桌面软件最合适的是：

> **一个权威 Agent Daemon + 一个受信工具宿主 + 按需原生 Worker + 多个薄客户端 + 进程内插件系统。**

这是“本地服务化的模块单体”，不是 Kubernetes 式分布式系统。它兼顾启动速度、故障隔离、可维护性和并行开发，避免形成新的分布式屎山。

### 0.2 语言决策

| 领域 | 目标语言 | 理由 |
|---|---|---|
| Agent loop、模型路由、上下文、记忆、技能、插件、工作流编排 | Python | 高频变化、生态成熟、无需本机长时间编译，适合快速迭代和热重载 |
| 文件/命令/进程/沙箱/权限强制/diff/revert | Rust | 属于受信执行内核，要求边界清晰、低级系统能力和稳定错误处理 |
| OCR、STT、Windows UIA、ONNX/Sherpa | 独立 Rust 或 Python Worker | 重原生依赖必须与基础聊天启动和普通开发隔离，按需启动 |
| 桌面壳 | 现有独立 Tauri Rust workspace | 只负责窗口、更新、进程监督、原生选择器和安全配对，不承载业务 |
| 桌面 Web UI | TypeScript + React + Vite | 组件化、类型化、领域目录、可独立热更新，结束全局变量和超大脚本模式 |
| ProductEval、批量评测、实验报表 | Python，开发时加载 | 不进入生产默认运行时，不应拖累用户启动和 Rust 编译 |

Rust 本身不是错误。Codex CLI 使用 Rust，但它把协议、app-server、core 和不同客户端拆成独立边界；其 CLI/TUI 还通过共享 app-server 客户端统一启动与生命周期。Hermes 使用 Python，同样不是因为“Python 自动解决架构问题”，而是它把 Agent loop、工具注册表、插件、Provider、会话存储和多个入口分成清楚的子系统。真正决定可维护性的因素是 **权威运行时、稳定协议、清晰所有权和可替换边界**。

### 1.2 为什么“最基本对话”仍不稳定

#### 问题 A：TUI、REPL、一次性 Turn 和桌面不是同一个运行时

当前 `tui.rs`、`commands/repl.rs` 和 `commands/turn.rs` 都会直接：

- 构造 `Agent`；
- 初始化模型 Provider；
- 连接 MCP；
- 打开同一个 `index.db`；
- 直接调用 `Agent::run_turn`。

桌面端则通过 Tauri 拉起 `owo-agent serve`，再访问 HTTP/SSE。也就是说，TUI 并不连接桌面后台；它本身就是另一套 Agent。用户看到的“服务连不上、状态不同、设置不一致”不是单一 UI bug，而是拓扑设计不一致。

直接后果：

- 多个进程可能同时拥有自己的工具注册表、授权内存、MCP 子进程和后台任务；
- TUI 中更改的运行态不等于桌面运行态；
- 会话数据库可能被不同运行时同时打开；
- 修复桌面服务不保证 TUI 修复，反之亦然；
- 同一功能需要在 HTTP、TUI、REPL 三条路径重复验收。

#### 问题 B：当前“流式输出”存在整段缓存

`gateway.rs` 的 `ResilientProvider::complete_stream_with_model` 为了避免重试造成重复 token，会先把所有 delta 写入 `Vec<String>`，只有整次流成功后才逐条调用 UI 回调。

这意味着底层模型即使正常 SSE 输出，用户仍可能长时间看不到任何 token，然后一次性看到整段文字。当前实现是“流式请求 + 非流式用户体验”。这是对话慢感知的 P0 根因。

正确策略：

- 首个 token 之前允许重试或切换 Provider；
- 首个 token 已经向用户发送后，禁止自动重放整轮；
- 中途断流返回 `provider/stream_interrupted`，保留已显示内容并提供“继续”动作；
- 每个 delta 直接进入有界事件队列，不能等待整轮成功。

#### 问题 C：MCP 连接阻塞服务监听

`commands/serve.rs` 在绑定本地端口和输出 `core_ready` 之前调用 `connect_mcp_clients`。该函数按配置串行连接，每个失败 MCP 最多等待 3 秒。

例如 8 个失效 MCP 最坏会在服务真正监听前额外等待约 24 秒。当前桌面壳又有 25 秒 ready-line 等待和后续 health 校验，多个可选集成即可把基础聊天拖入几十秒握手路径。

正确策略：

- 最小数据库和协议初始化完成后立刻监听；
- `core_ready` 只代表基础聊天面 ready；
- MCP、插件市场、感知模型在后台并发初始化，默认并发 2–3；
- 单个集成失败只把对应 capability 标成 degraded，不得拖死整个 Agent；
- 首次调用未就绪工具时再触发单飞初始化。

#### 问题 D：SSE 使用无界队列

`turn_api.rs` 使用 `mpsc::unbounded_channel` 转发 token、工具、审批和最终结果。当 UI 卡顿、窗口后台或消费断开时，无界队列可能积累事件和内存；它也没有明确背压策略。

正确策略：

- 改为有界队列；
- token delta 可在 20–50 ms 窗口合并；
- `tool_started`、`approval_required`、`tool_completed`、`final`、`error` 不允许丢；
- 队列拥塞必须有指标和稳定错误，不允许静默增长。

#### 问题 E：默认每轮把 34 个内置工具全部暴露给模型

`ToolRegistry::new()` 默认注册 34 个工具，包含文件、命令、子代理、OCR、视觉、桌面自动化和浏览器。之后还可能追加 MCP 工具。`Agent::run_turn` 每个模型回合都会组装当前全部可见 schema。

即使有 200 KB schema 压缩预算，也没有解决“简单聊天为什么要看到桌面点击、OCR、浏览器下载”等工具选择噪声。

正确策略：

- 工具按 `core-read`、`core-write`、`terminal`、`browser`、`desktop`、`perception`、`delegation`、`mcp:<server>` 组织为工具集；
- 每个平台和任务只启用必要工具集；
- 默认聊天只暴露 8–12 个基础工具；
- 通过 `tool_search` / `toolset_enable` 按需加载其他 schema；
- 工具 schema 指纹用于 Provider 前缀缓存，不在每轮做无意义重建。

#### 问题 F：功能数量远大于可用产品能力

当前后端有大量 route，前端有 15 个面板，但 `capabilities.rs` 只登记 7 个能力，并且全部是 Beta 或 Experimental，Stable 数量为 0。这说明“代码存在”与“用户知道它是什么、能点、能完成任务”之间没有闭环。

后续不得再用路由数、模块数、测试数代表产品进度。唯一进度单位是：

> 用户入口 + 明确用途 + 配置状态 + 权限说明 + 可执行动作 + 错误恢复 + 真实验收。

## 2. 目标架构

### 2.1 默认运行拓扑

```text
┌──────────────────────────────────────────────────────────────┐
│ Clients                                                      │
│ Desktop Web UI      CLI      TUI      IDE/未来 ACP           │
└───────────────┬──────────────┬──────────────┬─────────────────┘
                └──────────────┴──────────────┘
                         WebSocket / JSON-RPC v1
                                   │
┌──────────────────────────────────▼────────────────────────────┐
│ Agent Daemon（唯一权威运行时，目标 Python）                   │
│ Session/Turn/Item · Provider · Prompt/Context · Memory        │
│ Skill/Plugin · Toolset Registry · Streaming · Diagnostics     │
└───────────────┬───────────────────────┬───────────────────────┘
                │ framed JSON-RPC       │ on-demand RPC
                │ over stdio/pipe       │
┌───────────────▼────────────────┐  ┌───▼───────────────────────┐
│ Tool Host（小型 Rust 内核）    │  │ Perception Worker         │
│ Policy · Grant · Approval      │  │ OCR/STT/UIA/Vision/ONNX   │
│ FS · Command · Sandbox         │  │ 按需启动，可崩溃隔离      │
│ Diff/Revert · MCP execution    │  └───────────────────────────┘
└────────────────────────────────┘

开发时可选扩展：WorkSwarm / Eval / Fleet / Notes / Automation
```

### 2.2 各进程职责

#### Desktop Shell

只允许：窗口、托盘、Agent Daemon 生命周期、sidecar 身份校验、原生文件选择、更新和启动错误映射。禁止构造 Agent、访问会话库或复制模型/权限业务。

#### Agent Daemon

它是唯一产品后端和唯一会话写入者，负责 Session/Turn/Item、Provider、Prompt/Context、Memory/Skill/Plugin、工具集选择、流式事件和诊断。它不直接执行文件写入、命令和桌面控制。

#### Tool Host

它是小而稳定的受信执行内核，负责权限策略、授权、审批、capability 校验、工作区边界、文件/命令/进程、snapshot/diff/revert、MCP 安全代理和执行收据。Policy 与 Executor 必须在同一受信边界，不能让主 Agent 自批自执行。

#### Perception Worker

负责 UIA、OCR、ONNX、Sherpa STT、截图、视觉定位和 DesktopEnv/Scene 实验能力。默认不启动；崩溃时基础聊天、文件工具和设置页仍可用。

### 2.3 哪些应该拆，哪些不应该拆

| 当前能力 | 目标边界 | 独立进程 | 原因 |
|---|---|---:|---|
| Agent loop、Provider、Prompt、Context | Agent Daemon | 否 | 每个 token/工具回合都经过，跨进程只增加延迟 |
| Session、Turn、Message/Item 存储 | Agent Daemon | 否 | 必须保持顺序、幂等和单写者 |
| Memory、Skill、Context Engine | Daemon 插件 | 否 | 可替换但无需每次跨进程 |
| Provider 适配器 | Daemon 插件 | 否 | HTTP I/O 为主，服务化无收益 |
| Policy + Grant + Approval + Executor | Tool Host | 是 | 主 Agent 不能自批自执行 |
| 文件 snapshot/diff/revert | Tool Host | 否，和执行同进程 | 写入与恢复必须原子关联 |
| MCP | Daemon 管配置，Tool Host 执行 | 不按 MCP 再造服务 | MCP 本身已经是外部进程/HTTP 服务 |
| OCR/STT/视觉/UIA | Perception Worker | 是，按需 | 依赖重、启动慢、编译慢、崩溃风险高 |
| WorkSwarm/Goal/Workflow | Daemon 扩展 | 默认否 | 高级编排不应污染基础启动 |
| ProductEval/DatasetBuilder | 开发包 | 是，开发任务 | 不属于用户运行时 |
| Fleet/Cloud Exec | 可选扩展 | 是 | 仅远程节点场景加载 |
| Notes/Automation | Daemon 插件 | 否 | 插件接口足够，不必微服务化 |
| Web UI 页面 | 前端 feature | 否 | 共享设计系统、路由、缓存和连接状态 |

### 2.4 绝对不能拆散的事务边界

以下内容必须保持在一个拥有者内：

1. `User → Assistant tool_call → Tool result → Assistant final` 消息顺序；
2. turn 取消、超时、重试和终态；
3. 权限判定、capability、执行和审计收据；
4. 文件写前快照、写入、diff 和 revert；
5. 会话库迁移和消息持久化；
6. 桌面壳对子进程启动、版本配对和退出清理。

## 5. 协议、事件和数据所有权

### 5.1 对外核心模型

协议只保留三个一等对象：`Session`、`Turn`、`Item`。Item 覆盖用户消息、模型文本、reasoning、工具调用、审批、工具结果、diff 和错误。

统一事件信封：

```json
{
  "protocol_version": "1.0",
  "event_id": 1024,
  "session_id": "s_...",
  "turn_id": "t_...",
  "item_id": "i_...",
  "kind": "assistant.delta",
  "sequence": 17,
  "timestamp": "2026-09-19T12:00:00Z",
  "payload": {}
}
```

要求：event id 单调递增、客户端可按游标恢复、同一 turn 顺序稳定、终态只有 completed/failed/cancelled、重复事件幂等、旧 HTTP/SSE 只做 compatibility adapter。

### 5.2 Daemon 与 Tool Host 协议

使用 length-prefixed JSON-RPC 2.0 over stdio 或 Windows named pipe。第一阶段优先 stdio 子进程协议，避免端口、CORS 和 token 配对问题。

基础方法：

```text
tool/catalog        tool/authorize       tool/execute
tool/cancel         approval/list        approval/respond
grant/list          grant/revoke         execution/read
health/read
```

`tool/authorize` 返回 allowed、denied、approval_required 三态。allowed 必须携带短时 capability，至少绑定 tool name、canonical args hash、workspace/session/turn、effect、scope、expiry 和 nonce。Tool Host 只接受自身签发且未过期的 capability。

### 5.3 数据所有权

| 数据 | 唯一写入者 | 目标存储 |
|---|---|---|
| session/message/turn/item | Agent Daemon | `state.db`，WAL，单写队列 |
| memory/skill metadata | Agent Daemon | `state.db` 或插件自有库 |
| grant/pending approval/policy audit | Tool Host | `policy.db` |
| execution receipt/diff/revert | Tool Host | `execution.db` |
| artifact metadata/CAS | Agent Daemon | `artifacts.db` + immutable CAS |
| OCR/STT cache | Perception Worker | 可删除 cache，不是权威状态 |
| eval result | Eval devtool | 独立目录/库，不进用户 state |

禁止两个服务共享同一 SQLite 写库；禁止 TUI/CLI 直接打开 state.db；禁止 Artifact Review 与 WorkSwarm 继续通过独立连接共同修改 space.db。

### 5.4 工具集和插件

工具 manifest 是模型 schema、UI 说明、权限风险、CLI help、测试样例和 capability 成熟度的单一来源。插件可注册工具、Hook、Provider、Memory、Context Engine、UI tab 和后台任务，但不能修改核心稳定提示前缀、绕过 Tool Host、直接写其他插件数据库或在基础 ready 前执行长初始化。

## 6. 启动与性能设计

### 6.1 冷启动阶段

```text
Shell visible
  → spawn Agent Daemon
  → bind control channel
  → open/migrate state.db
  → emit chat_ready
  → UI enables conversation
  → background warm Tool Host and discover plugins/MCP
  → perception remains stopped
```

健康状态必须分阶段返回 process、chat、tool_host、mcp、perception 和 extensions。基础聊天不能等待 MCP、OCR/STT、插件市场、WorkSwarm 恢复、ProductEval 扫描或报表生成。

### 6.2 真流式规则

1. Provider token 立即转为 `assistant.delta`；
2. 首 token 前可重试，首 token 后禁止无提示重放；
3. UI 每 16–33 ms 批量刷新 DOM，后端不整轮缓存；
4. 队列有界，token 可合并，控制事件不可丢；
5. 客户端重连按 cursor 补发，不重新执行 turn；
6. 存储 append item，不在每个 token 重写整份 Session。

### 6.3 工具调用快路径

```text
model tool_call
  → Daemon validate schema
  → Tool Host authorize
  → allow: execute immediately / ask: approval item
  → Tool Host executes with capability
  → result preview + artifact ref
  → Daemon appends tool result
  → next model call
```

Daemon 到 Tool Host 连接常驻；路径 canonicalize、workspace id、schema 和策略编译结果按代际缓存；只读工具有界并发；大结果只返回 preview + artifact；MCP 长连接和单飞重连。

### 6.4 目标 SLO

| 指标 | A0 目标 | 最终目标 |
|---|---:|---:|
| 窗口可见 P95 | ≤ 1.5 s | ≤ 0.8 s |
| 基础聊天 ready P95 | ≤ 3 s | ≤ 2 s |
| Provider 首 token 额外转发开销 P95 | ≤ 150 ms | ≤ 75 ms |
| Tool Host 空 RPC 开销 P95 | ≤ 50 ms | ≤ 20 ms |
| 审批卡可点击 P95 | ≤ 200 ms | ≤ 100 ms |
| 取消确认 P95 | ≤ 500 ms | ≤ 200 ms |
| 基础启动受坏 MCP 影响 | 0 s | 0 s |
| 普通 Agent/Python 改动触发 Rust 编译 | 0 次 | 0 次 |

每项必须保存 P50/P95、样本数、机器信息和 raw trace，不能只写“明显变快”。

## 7. 前端产品架构

默认用户只看到五个一级入口：对话、项目、工具与权限、产物、设置与诊断。WorkSwarm、Fleet、Eval、WorldModel、模板市场全部放入“实验功能”，默认隐藏且不自动请求数据。

TypeScript 目标目录：

```text
src/
  app/           # 启动、路由、错误边界
  platform/      # Tauri/browser adapter
  rpc/           # generated client + events
  state/         # connection/turn/session
  ui/            # 统一控件
  features/{chat,projects,permissions,artifacts,settings,diagnostics}/
  extensions/workswarm/
```

每个 feature 只能通过生成客户端访问后端，具备 loading/empty/error/ready 四态、键盘操作、可访问性、测试和 dispose/abort。枚举必须用 Select/Radio/Checkbox，文件目录用原生选择器，不可用按钮必须解释原因，原始 JSON 设置只在开发者模式显示。

## 8. 并行开发模型

| Lane | 独占目录 | 日常验证 |
|---|---|---|
| Contracts | `packages/contracts` | schema lint + codegen + consumer tests |
| Agent Runtime | `services/agentd` | ruff + pyright + pytest |
| Tool Host | `services/tool-host` | 定向 Rust，最多 `-j 2` |
| Perception | `services/perception-worker` | 独立 workspace 定向验证 |
| Desktop Shell | `apps/desktop-shell` | 壳单测 + 定向构建 |
| Desktop UI | `apps/desktop-ui` | typecheck + unit + browser E2E |
| Extension | `extensions/<name>` | 插件契约 + 自身测试 |

跨 lane 先改 contracts，不直接改内部文件；CI 按路径触发；完整桌面矩阵只在协议、壳、发布或里程碑变更时运行；扩展失败不能阻止基础聊天发布；禁止多个 Agent 同时编辑根路由、共享 schema 或同一迁移。

验证矩阵：

| 改动 | 必跑 | 不应默认跑 |
|---|---|---|
| Python Agent/Provider | Python 单元、对话回放、协议 | Rust core、ONNX、Tauri release |
| Web UI | typecheck、组件、Playwright 基础路径 | Cargo workspace |
| Tool Host 文件工具 | tool-host 定向 Rust + contract | perception、Tauri release |
| OCR/STT | perception workspace | Agent Daemon 全套 |
| Contract | codegen + 三端 consumer | 真机矩阵，除非破坏兼容 |
| Shell/sidecar | 壳测试、冷启动、版本配对 | ProductEval/WorkSwarm 全评测 |
| Release | 全链、安装包、真机矩阵 | — |

## 9. 分阶段迁移计划

### A0：冻结扩展，修复基础产品快路径（最高优先级）

#### A0.1 修复假流式

文件：`core/gateway.rs`、`core/agent.rs`、`server/turn_api.rs`、`desktop/web/app-domain.js`。

修改：删除 ResilientProvider 整轮 delta 缓存；首 delta 前允许 retry/fallback，之后断流返回稳定错误；SSE 有界队列和 delta coalescer；UI 保留已输出文本；trace 增加 provider TTFB、first UI delta、stream end。

验收：真实请求期间文本逐步增长；网络中断不重复 token；断流后可继续新回合。

#### A0.2 启动链最小化

文件：`cli/commands/serve.rs`、`cli/support.rs`、`tauri/core_runtime.rs`。

修改：先创建最小 Agent/DB、绑定端口并输出 chat-ready；MCP 后台有界并发；插件/技能/感知分别上报；壳只按 chat-ready 允许对话；收敛 25+10+15 秒叠加等待。

验收：加入 10 个不可达 MCP，基础聊天 ready 相比无 MCP 增加不超过 200 ms。

#### A0.3 工具集收敛

文件：`core/tools.rs`、`core/agent.rs`、`server/capabilities.rs`。

修改：`ToolRegistry::new()` 不再等于全量 34 工具；旧行为改名 `full_legacy()`；新增 ToolsetRegistry 和最小 default_chat；桌面/浏览器/感知按需启用；capability 从 manifest 生成。

验收：简单聊天 schema 明显缩小；文件读取闭环；未启用桌面工具时模型看不到 click/type。

#### A0.4 基本黄金路径

```text
双击启动 → 新建会话 → 普通问题真流式
→ 列出/读取工作区文件 → 请求修改并审批“仅本次”
→ 显示 diff → 撤销恢复 → 重启后会话恢复
```

只有该真实 E2E 通过才进入 A1，任何新功能不得插队。

### A1：建立单一协议源

新增 `packages/contracts/schemas/core`、生成器和 `tests/contract`。定义 Session/Turn/Item/Event/Error/Capability/Tool RPC；生成 Rust/Python/TS；旧 HTTP/SSE 作为 v0.7 adapter；WorkSwarm 协议移出 core。

退出条件：三语言由同一 schema 生成；基础协议不依赖 WorkSwarm 类型。

### A2：统一权威 Daemon，先不换语言

先继续使用现有 Rust server 充当 compatibility daemon：CLI/TUI/REPL/Turn 全改 RPC 客户端，删除直接 Agent/SQLite/MCP 路径；同一 profile 只有一个 daemon 写状态。

新增 `crates/owo-agent-client`。退出条件：源码搜索确认客户端不再引用 `Agent`、`SqliteSessionStore`、`connect_mcp_clients`；同时打开桌面和 TUI 不产生第二套 runtime。

### A3：隔离重原生依赖

新建 `services/perception-worker` workspace，迁移 OCR/ONNX、STT/Sherpa、UIA、视觉和感知实验能力。随后从基础 core 删除 `ort`、`sherpa-onnx`、`ndarray` 和不必要 Windows feature。

退出条件：修改 Agent/Provider/Session 不构建 ONNX/Sherpa；perception 未安装或崩溃时基础聊天和文件工具正常。

### A4：抽取 Tool Host

迁移顺序：只读文件工具 → 写入+diff/revert → command/process → permission/grant/approval → MCP → browser/desktop action。

每个工具走 shadow、canary、cutover 三阶段。退出条件：Daemon 无直接文件写和命令路径；每次执行有 receipt；权限不可绕过。

### A5：高频 Agent 逻辑迁到 Python

技术栈：Python 3.12、uv、asyncio/FastAPI、Pydantic v2、httpx、pytest/anyio、ruff、pyright；发布使用 one-folder sidecar，禁止 one-file 每次启动解压。

顺序：Provider 真流式 → Prompt/Context → Session/Turn/Item → Tool loop → Memory/Skill → Plugin/Hook → Goal/Workflow → WorkSwarm 最后。

每步用固定任务对比 Rust/Python 的事件顺序、工具参数、审批、终态、取消和错误码。黄金路径和性能达标后才删除 Rust Agent loop。

### A6：前端 TypeScript 化

按 connection shell → chat → permissions → settings/diagnostics → projects/artifacts → experiments 迁移。旧面板通过 legacy adapter 临时挂载；完成一个 route 即删除其旧全局变量和轮询。

### A7：插件化与死代码清算

每个高级模块四选一：Stable core、默认 extension、devtool、删除。没有入口、契约、诊断和真机验收的模块不得进入 release 默认包。

## 10. Rust 资源红线继续生效

1. 定向 Rust：`CARGO_BUILD_JOBS=2`、`RUST_TEST_THREADS=2`、`-j 2`；
2. 完整 workspace/core/release/原生重链：`-j 1`、`--test-threads=1`；
3. 禁止并行两组 Cargo；
4. 可用内存 <6 GB 或已用 ≥80% 不得启动；
5. 完整构建卷剩余 <20 GB、定向 <6 GB 不得启动；
6. Cargo 前经 `Resolve-OwoOrtEnv`，直到 A3 完成；
7. 禁止 `--quiet` + 截尾隐藏进度；
8. 长任务走 `Invoke-CiCargo` 心跳、资源门和真实退出码；
9. 普通 Python/TypeScript/协议修改不得顺带跑 Rust 全链；
10. 完整发布验证与日常开发验证分开。

最终预期：绝大多数 Agent 功能迭代完全不调用 Cargo；只有 Tool Host、Perception 或 Shell 修改才编译对应 workspace。

## 11. Bug、占位和死代码治理

功能成熟度：`proposal → implementation_only → contract_ready → integration_ready → product_ready → stable`。默认 UI 只显示 product_ready/stable。只有源码或测试的功能必须显示实验/未验收。

删除候选：无生产入口、两个版本周期无 owner、与新 service 重复、只返回 mock/demo、共享数据库所有权冲突、依赖 blanket allow 且无里程碑。

反复 bug 必须记录：用户症状、错误码、首次失败边界、权威状态拥有者、测试漏检原因、最小修复、架构防复发、真机验收。禁止只靠延长超时和增加重试结案。

## 13. 完成定义

只有同时满足以下条件才能写“架构重构完成”：

- 桌面、CLI、TUI 连接同一权威 Daemon；
- 黄金路径在安装包真实通过；
- token 真流式，无整轮缓冲；
- 坏 MCP/Perception/实验插件不阻塞聊天；
- Daemon 不直接执行高风险系统工具；
- Tool Host 权限不可绕过；
- 每个 SQLite 只有一个服务写入者；
- Agent/Provider/Prompt/UI 修改不触发 Rust/ONNX 全链；
- 核心协议由单一 schema 生成三语言类型；
- Stable capability 覆盖会话、流式对话、文件读写、命令、审批、diff/revert、诊断；
- 默认 UI 没有点不开或只有占位数据的功能；
- 冷启动、首 token、工具、审批、取消有 P50/P95；
- release 中 shell、daemon、tool-host、协议版本和 manifest 可核对；
- Rust 资源红线仍由脚本强制。

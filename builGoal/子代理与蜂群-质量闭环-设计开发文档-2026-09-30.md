# 子代理与蜂群 · 质量闭环 设计开发文档（2026-09-30）

> 范围：Step 1（子代理可见性 / 审批打通 / 预算自适应 / 并行探索 / headless 子代理可交付）、
> Step 2（CLI `/team` 接入 WorkSwarm）、Step 3（父侧自动复核 + 有界返工）。
> 结论口径：所有条目都有可复现证据（测试名或真实模型 E2E 日志片段）。

---

## 0. 问题定义（用户原话）

1. 子代理"完成的任务都是草草了事，完成质量也不高"——只报完成、不验对错；
2. 子代理调用工具需要审批时**无法传给用户**，"导致任务超时卡死"；
3. 已有的蜂群（WorkSwarm）能让多个 Agent 同时干活、自动分配任务，但 CLI 够不着。

## 1. Step 1：子代理可见性 + 审批打通 + 预算 + 并行

### 1.1 事件下沉（`SubagentRunner.events`）

- 新增 `subagent::TurnEventSink<'a> = Arc<dyn Fn(&TurnEvent) + Send + Sync + 'a>`；
  `SubagentRunner` / `ContractSubagentRunner` 各加 `events: Option<TurnEventSink<'a>>`。
- `Agent::run_turn` 把调用方的 `on_event` 放进共享单元
  `agent::EventCell<'a> = Arc<Mutex<&'a mut (dyn FnMut(&TurnEvent) + Send + 'a)>>`，
  并派生 `nested_sink` 传给每个子代理；父回合自身的事件也走同一单元
  （所以子代理在父回合 await 期间也能即时回传，不存在"缓冲到组结束才回放"的死锁）。
- 转发过滤：`PermissionRequest` / `ModelCall` 原样转发；`ToolStart` / `ToolResult`
  加 `sub:` 前缀（标明来源，id 保持配对）；`TokenDelta` / `Final` / `Compaction`
  **不外发**（否则子代理的流式文本会混进父代理的回答）。
- 锁中毒容错：`unwrap_or_else(|poisoned| poisoned.into_inner())`——静默丢弃事件比
  "带毒继续"危险（实测：用 `if let Ok` 时，一次中毒会让 SSE 事件全部消失）。

### 1.2 审批打通（"卡死"根因）

- 直呼子代理（goal/plan 的 `AgentWorker`、`POST /subagent`）没有审批回传通道，
  旧实现用 `AutoApprover { allow: read_only }`：producer 的写/执行**一律被拒**，
  或阻塞在永远到不了的审批上直到超时。
- 新增 `permissions::WorkspaceApprover { workspace, allow_writes }`：
  `Read` 恒放行；`Write` 仅工作区内（相对/绝对路径、去 `\\?\` 前缀、新建文件按
  最近存在祖先判定）；`Execute`/`Inject` 仅 `allow_writes` 时放行；越界一律拒绝。
  `Agent::run_subagent` 改用它。
- 交互路径（CLI 本地/daemon）不变：审批请求现在经 1.1 的事件下沉**即时**到达客户端
  （daemon 走 SSE → CLI 弹卡 → `POST /session/{id}/permission/{request_id}` →
  `ChannelApprover` 的 oneshot 收到决定）。

### 1.3 预算自适应

- `contract_worker::adaptive_subagent_turns(prompt, read_only)`：
  基础值（只读 10 / 通用 16）+ 每 200 字符 +1，上限（只读 24 / 通用 40），
  再与调用方配置取小（配置是硬上限）。替换原来的固定 `min(12)`。

### 1.4 `explore` 并行多问题

- `explore` 支持 `queries: [string]`（最多 8 个，并行 `join_all`），
  返回 `{mode, parallel, truncated, results:[{query, ok, text|error}]}`；
  单个 `query` 仍兼容。

| 项 | 证据 |
|---|---|
| 事件转发 | `loop_tests::subagent_tool_forwards_nested_events_to_parent_stream`、`contract_worker_tests::nested_subagent_forwards_permission_and_tool_events` |
| 预算自适应 | `contract_worker::budget_tests::adaptive_budget_scales_with_prompt_and_role` |

## 2. Step 2：CLI `/team` 接入 WorkSwarm

命令面（daemon REPL，`owo-agent repl`，自动拉起 daemon）：

```
/team <目标>          创建团队（POST /teams，mode=team、strategy=auto、绑定当前工作区）并实时跟踪
/team list            团队列表（active / interrupted 标记）
/team use <团队ID>     切换当前团队
/team status          任务图 + 成员 + 审计尾迹（GET /teams/{id}）
/team watch           继续跟踪（Ctrl+C 只停跟踪，团队继续后台跑）
/team steer <说明>     POST /teams/{id}/steer {"command":"steer"}
/team retry <步骤ID>   POST /teams/{id}/steer {"command":"retry"}
/team cancel           POST /teams/{id}/steer {"command":"cancel"}
/team diff             GET /teams/{id}/change-sets（真实变更集 + 批准门原因）
```

- 跟踪循环：2s 轮询，打印任务状态转移（`▶ 开始执行` / `✔ 完成` / `✘ 失败`），
  终态即收尾；10 分钟上限 + Ctrl+C 都只"放手"不取消团队。
- 工作区绑定：`workspace: { root: <当前工作区>, read_only: false }`（写角色才真正落盘）。

**E2E 证据**（真实模型 + 真实 daemon）：

```
✓ 团队已创建：team-e532749a（Team · 动态组队）
  ▶ builder 开始执行 → ✔ builder 完成 → ✓ 团队终态：succeeded
工作区：team_demo.txt（13 字节）
```

## 3. Step 3：质量门（自动复核 + 有界返工）

### 3.1 两个"草草了事"的真实根因（本批修掉）

1. **通用交付角色被判成只读**：`WorkerProfile::for_role` 的写角色关键词只有
   `implementer/builder/finalizer/drafter`，而 `producer_role_name` 对未知分类返回
   `"producer"`、forced team 用 `"leader"`、文档族用 `"writer"` → 这些角色落到只读分支，
   **团队"成功"却零产出**。修法：关键词补 `producer/writer/leader`（研究族判定在前，
   `brief_writer` 仍只读）。
2. **单 Agent 裁剪裁错角色**：`trim_to_single` 保留**首个**角色，而默认接力首个是只读
   `planner` → 单 Agent 团队天然不交付。修法：优先保留**可交付（写）角色**，
   并清空其 `depends_on`（上游已裁掉，保持 DAG 可拓扑排序）；没有写角色（研究类）
   才保留首个。

   回归测试：`worker_profile::tests::generic_producer_writer_leader_roles_are_writers`。

### 3.2 父侧自动复核 + 一次返工

- `subagent` 工具返回后，自动起一个**只读 critic 子代理**独立核对：
  `contract_worker::review_prompt(task, output)`（逐条核对验收标准、无证据视为未完成、
  给出可执行返工清单）；结论按契约放进 `summary` 的 `{"approved":bool,...}`。
- `critic_approved(text)` 解析结论（兼容 summary 内嵌 JSON / 裸 JSON / 围栏；
  解析不到 → `None`，**不误判为通过**）。
- 不通过 → `rework_prompt(task, previous, review)` 返工**一次**（有界，不无限重试），
  返工结果即委派结果；工具返回体带 `review: {approved, reworked, critic}`。
- 复核本身失败不阻断交付（best-effort，返回 `review.error`）。
- 开关：`OWO_SUBAGENT_REVIEW=0|false` 关闭（成本/延迟敏感时）。
- 子代理 system prompt 增加"验收纪律"：先明确验收标准、结论必须带证据（写进
  `evidence` 字段），无证据的完成声明会被复核判为未完成。

**验证**：`loop_tests::subagent_review_failure_triggers_one_rework`
（复核 `approved:false` → 返工消耗一次调用，父代理拿到返工后的交付）、
`contract_worker::review_tests::*`（结论解析 + 提示词携带任务与复核意见）。

## 5. 已知问题 / 后续

1. **团队审计尾迹中文变 `?`**（如 `目标达成：?????`）：疑似服务端持久化/读取链路
   有损编码，未定位（本批未动 audit 存储）。
2. **写角色工具面仍是 5 件套**（`read_file/write_file/list_dir/search_files/run_command`）：
   `edit_file`/`apply_patch` 需要"白名单包装"版本（`WhitelistWriteFileTool` 只包了
   write_file），否则会绕过角色写白名单——留待后续统一。
3. **复核成本**：默认开 = 每次 `subagent` 多一次只读回合；批量委派场景可用
   `OWO_SUBAGENT_REVIEW=0` 关闭。
4. **`/team` 的 `accept/reject/revert`** 尚未做成 CLI 命令（现只在 `/team diff`
   末尾提示 HTTP 路由）。
5. **daemon 锁 exe**：重建前需先结束 `owo-agent` 进程（否则 `cargo build` 报
   "拒绝访问"）。

## 6. 十一期：`/team` 并行开发（2026-10-01）

用户诉求：**不是多个角色**，而是多个 agent 同时干同一个活；靠调度与任务主动分配
把墙钟打下来，明显快过单 agent。**配置要统一到一个文件并支持自定义**（不是散落的
CLI 常量/角色分模型）。

### 6.1 真实瓶颈（探索结论）

1. 默认接力 DAG（planner → builder → critic → leader）串行，写者只有一个；
2. 即使多写者同时就绪，`TrackedRoleWorker` 用单一全局 `Mutex` 写锁串行化全部落盘；
3. 没有"拆解 → 并行执行 → 汇总"的主动分配机制；`RoleSpec`/模板无写范围字段
   （全队写面 = 整个工作区，即使并行也互相排他）；
4. 团队默认值此前散落在 CLI 常量里，无法由用户按工作区统一配置。

core 调度本身已并行（`JoinSet + max_parallel`），缺的是并行编排、动态分配与统一配置。

### 6.2 改动

- **A · 统一配置（一个文件 + 可自定义）**：`<workspace>/settings.json` 新增
  `team` 段（core `TeamSettings`，随既有 Settings 读写/热重载，`GET/POST /settings`
  自动可见可存）：

  ```json
  {
    "team": {
      "model": "glm-5.3-flashx",
      "parallel": 4,
      "max_parallel": 4,
      "roles": [
        { "role": "lead", "assignee": "agent", "worker": "agent" },
        { "role": "w1", "assignee": "agent", "worker": "agent", "depends_on": ["lead"], "write_paths": ["src/auth"] },
        { "role": "w2", "assignee": "agent", "worker": "agent", "depends_on": ["lead"], "write_paths": ["src/order"] },
        { "role": "leader", "assignee": "agent", "worker": "agent", "depends_on": ["w1", "w2"] }
      ]
    }
  }
  ```

  - 服务端建队（`POST /teams`）读该段补缺省：请求显式字段 > `team.*` >
    `Settings.model` > 环境变量/内置缺省；**CLI/UI 不写死模型**；
  - `team.roles` 支持完全自定义编排（`depends_on`/`model`/`write_paths`/`worker`），
    请求未给角色且未指定模板时生效；
  - `team.parallel`（2..=8）缺省启用并行（自动生成 `parallel_roles(N)`）；
    `team.max_parallel` 控制同一 wave 并发度；角色含 `lead` 时自动启用动态分配。
- **B · 数据模型（additive）**：`CreateTeamRequest`/`POST /teams` 增加
  `model`/`parallel`/`max_agent_members`；`RoleSpec`/`TeamTemplateRole` 增加
  `model`/`write_paths`；`GoalBudget.max_parallel`（缺省 4，1..=8）→
  `RunnerConfig.max_parallel`，并行度可控。解析优先级：
  `extra_input.model` > `RoleSpec.model` > 团队 `model`。
- **C · 并行开发模式**：核心提供 `workswarm::parallel_roles(N)`：`lead`（只读拆解）
  → `w1..wN`（只依赖 lead，同一 wave 真并行）→ `leader`（依赖全部 writer，汇总交付）。
  - **任务主动分配**：lead 被契约约束输出裸 JSON
    `{"subtasks":[{worker,task,write_paths,acceptance}]}`；运行期（`run_phase`
    阶段 C）解析该产物，把每条子任务**动态**写入对应 writer 的
    `RunMeta.roles[].write_paths`（下次注册表重建即收窄写范围/升级为写角色）
    与 `handoff_contract`（子任务进 Prompt），并同步步骤输入
    `assigned_task`/`assigned_write_paths`（可观测）；幂等、无变化不落盘；
    用户 `--write`/配置里预声明的写范围优先，lead 不得改写。
  - 解析失败/写路径非法 → 保持 writer 原权限（缺省只读）并记
    `team.parallel_assign_skip` 审计——**绝不因调度信息缺失而放宽权限**。
- **D · 范围写租约**（server `workswarm_api/write_lease.rs`）：未声明写范围 =
  工作区级全局互斥（默认行为不变）；声明且互不重叠（路径前缀无交集）的写角色
  并发落盘，重叠者排队。`TrackedRoleWorker` 做**窗口归属过滤**：租约已释放范围
  保留有界历史，把「本步骤窗口内其他写者范围内」的路径排除出越界判定与
  ChangeSet——并发新文件不误判越界、不互抢 diff；范围外且窗口内干净、无并发
  写者可归因的路径仍判 `scope_violation`。
- **E · CLI**：参数只作为「显式覆盖」，缺省全由 settings.json 决定：

  ```
  # 配置里写了 team.parallel=4 → 直接并行；命令行也可显式指定
  /team --parallel 4 "重构订单模块：拆分校验/价格/库存/通知四块"
  /team --model glm-5.3-flashx --parallel 3 --write w1=src/auth "并行实现鉴权"
  ```

  自定义角色（高级）：`--role <名[:依赖1|依赖2]>` + `--write <角色>=<路径>`；
  `--model <角色>=<模型>` 为角色级覆盖。

### 6.4 边界与残余风险

- **不支持同文件并发写**：写范围重叠即排队（路径前缀判定），越权语义不变；
  lead 被要求把写范围拆到互不重叠，但未强制校验重叠（重叠只会退化并发度）；
- lead 拆解失败（产物不可解析）→ writer 保持只读，只交付 Artifact 不落盘，
  并留 `team.parallel_assign_skip` 审计；
- `run_command` 仍可越过 `write_file` 白名单：声明范围的并行写者只对「本范围 +
  窗口内无并发写者可归因」负责；越界且窗口内干净仍会 `scope_violation`；
- 写范围是与团队绑定白名单的交集；两侧非空且无交集时用不可达哨兵路径拒绝一切
  写入（不会退化成"工作区内可写"）。

## 1. F-02 真流式修复（P2.1）

### 问题
`crates/owo-agent-core/src/gateway.rs` 的 `ResilientProvider::complete_stream_with_model`
把增量收进 `let mut deltas: Vec<String>`，整条成功后 `for delta in deltas { on_delta(delta) }`
回放——用户看到的是"整轮结束一次性刷出"，而不是逐 delta 实时显示。真机证据：
`stream_span_s=0.0`、首 delta 与 final 几乎同时到达（`buffered_suspected=true`）。

### 修复
改为**立即回调**：`on_delta` 在增量产生时就调用。代价与约束：
一旦已有增量发出，重试/降级都会造成重复内容，因此此时**只失败、不重试也不降级**
（显式错误"流式中断：已输出部分内容，不再重试以免重复"）；未产生任何增量时保留原重试/降级。

### 回归测试（`gateway::tests`）
- `resilient_streams_deltas_immediately_and_does_not_retry_after_emit`：
  先吐 2 个增量再失败 → 断言增量**已经**到达（旧实现为 0）+ 只调用 1 次（不重试）。
- `resilient_still_retries_before_any_delta`：第一次连接失败（无增量）、第二次成功吐增量
  → 断言重试 1 次且增量只出现一次。

### 真机验证
`mk-smoke.ps1 -Tag p2-stream -Build -RealTurn`：

```
real_turn.multi_delta       delta_count=54
real_turn.first_delta...    first_delta_latency=11.99s stream_span=1.96s final_latency=13.95s
report.real_turn.buffered_suspected = false   ← F-02 已消除
```

## 2. MCP 就绪延迟上界（P2.3）

### 问题
`connect_mcp_clients` 逐个串行连接，每个 3s 超时 → N 个坏 MCP 就是 3N 秒，
"坏 MCP 不影响 3 秒内 ready"在 N≥2 时不成立。

### 修复
改为 `tokio::task::JoinSet` **并发连接 + 全局 3s 预算**：无论多少个坏 MCP，
就绪延迟都被钉在 3s 内；超时后 `abort_all` 清理未完成握手。

### 真机验证
两个会挂 30s 的 MCP（`powershell Start-Sleep 30`）注入 `mcp-servers.json`：

```
core_ready_ms=3608   （进程启动 + 3s MCP 预算 + 约 0.6s 其它初始化）
```

（旧实现应为 3s×2 + 启动 ≈ 6s+。）

已自动化为可重复脚本 `scripts/verify-mcp-readiness.ps1`：

```
[mcp-readiness] bad_servers=3 core_ready=3.29s（上限 6s）   exit=0
```

即 N 个坏 MCP 下就绪时间不再随 N 线性增长（旧实现 3N 秒）。

## 2b. Turn cancellation 贯穿（P2.5）

链路（源码事实）：
- 客户端 `cancel_turn` → `POST /session/{id}/abort`（`owo-agent-client::turns`）；
- 服务端 `abort_turn` 置位 `aborts` 表中的 `AtomicBool`；
- 回合流被丢弃（客户端断开）时 `stream_abort.store(true)`（`turn_api.rs`）；
- Agent loop 在每个模型/工具阶段检查 abort，并用 `wait_for_abort` 与在途 future 竞速
  （`agent.rs`，含并发组 `abort_during_concurrent_group_cancels_pending_tools` 测试）。

CLI（`turn`/`repl`/`tui`）均已接 Ctrl+C → `cancel_turn`。客户端路由由
`client_contract_tests::client_round_trips_against_fake_daemon` 覆盖（断言 abort 返回 ok）。

## 4. Trace P50/P95 脚本（P2.7）

新增 `scripts/trace-perf.ps1`：
- 读取 `<traces>/*.json`（`TraceRecord.duration_ms` + `phase_timings[]`）；
- 输出回合 duration 与各阶段（含 `first_token_ms`）的 P50/P95/max；
- Core trace writer 在隔离基准 Daemon 配置 allowlisted `OWO_PERF_TASK_ID` 时写入 `performance_task`；报告器按指南 8 项固定任务分组，默认每项至少 20 个样本，未标记 trace 仅计入探索性汇总；
- JSON 与 Markdown 均记录机器/OS/架构、Git commit 与 dirty 状态、脱敏后的 Provider endpoint 及其环境/源码默认来源、模型、样本数和原始 trace 路径；默认报告写入 `docs/qa/logs/trace-perf-<ts>.json`；
- 任一固定任务样本不足时显式退出 2；`-AllowUnclassifiedAggregate` 仅允许探索性总览成功退出，不改变报告中的未覆盖状态。
- `TraceRecord` 新增可选 `performance_task`（旧 trace 默认空且未标记 trace 的 JSON 形状不变）；Daemon 仅在进程环境 `OWO_PERF_TASK_ID` 命中指南 8 个固定 ID 时写入标签，未知值会忽略。Core trace 代码 `cargo clippy -p owo-agent-core --lib --locked -j 1 -- -D warnings` 于 2026-09-22 在 T 盘通过。

2026-09-22 用现存 1 条真实回合 trace 验证：PowerShell 5.1 下 JSON/Markdown 均成功生成；该 trace 没有任务标签，报告记为 `unclassified_traces=1`，8 项任务均为 `not_measured`。探索模式 exit 0 且状态 `task_coverage_incomplete`；严格模式报告落盘后 exit 2。该结果只证明报告器口径与门禁正确，**不代表**指南要求的固定任务已运行；真实任务 20 次/项、对应 SLO 和版本间 baseline 仍未完成。

探索性汇总样例：

```

  回合 duration_ms：p50=10002 p95=10002 max=10002
  阶段 model        elapsed p50=9996 p95=9996；first_token p50=9996 p95=9996
[trace-perf] 探索性汇总通过；固定任务覆盖仍未通过。
```
